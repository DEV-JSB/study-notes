# 문자열과 GC

> Unity · C# 런타임 · 2026-08-08 — 그림 버전은 [string-gc.html](string-gc.html)
>
> 실습 원본: [unity-study / 02.StringGC](https://github.com/DEV-JSB/unity-study/tree/main/Assets/Chapter/02.StringGC)

[1편(박싱)](boxing-dictionary.md)은 와닿지 않았다. `IEquatable` 없는 struct 키는 실무에서 거의 안 나온다. 그래서 **매일 쓰는 문자열**로 옮겼다. `+`, `$""`, `string.Format`, `StringBuilder` — 무엇이 박싱하고, 무엇이 GC를 얼마나 만드나.

**한 줄 결론: 만드는 방법을 바꾸면 최대 15% 차이, 값이 바뀔 때만 만들면 66배 차이.**

## 1. 측정 결과 (직접 측정)

Unity 6000.0.72f1 · 에디터(Mono) · Profiler GC Alloc · 프레임당 6,000회 · 1–4번은 `i`(0–5999), 5번은 `i / 60`(0–99)

| 케이스 | 프레임당 | 개당 | 내역 |
|---|---|---|---|
| 1. `"Score : " + i` | 441.0 KB | 75.3 B | 중간 문자열 + 최종 문자열 |
| 2. `$"Score : {i}"` | 384.6 KB | 65.6 B | 박싱 + 최종 문자열 |
| 3. `string.Format("Score : {0}", i)` | 384.6 KB | 65.6 B | 박싱 + 최종 문자열 |
| 4. `StringBuilder` (+ `Clear`, `ToString`) | 441.0 KB | 75.3 B | 중간 문자열 + 최종 문자열 |
| 5. 값이 바뀔 때만 생성 | **6.6 KB** | — | 문자열 100개만 |

## 2. 문자열 하나의 크기 (계산)

**22 + 글자수 × 2** 바이트

```
┌──────────┬────────┬──────────────────────┬──────┐
│ 헤더 16  │ 길이 4 │ 글자 × 2 (UTF-16)     │ 널 2 │
└──────────┴────────┴──────────────────────┴──────┘
```

- 예: `"Score : 5999"`는 12글자 → 22 + 12 × 2 = **46 B**

## 3. 한 줄 실행하면 힙에 무엇이 생기나

Profiler가 잡는 건 **그 줄을 실행하는 동안 힙에 새로 생긴 것 전부**다. 결과 문자열 하나만 생기는 게 아니라, 만드는 도중에 잠깐 쓰고 버리는 것도 같이 잡힌다. 그래서 개당 측정값(65.6 B, 75.3 B)이 결과 문자열 크기보다 크다.

`i = 5999`일 때 한 번 실행하면:

**2·3번 — `$"Score : {i}"`, `string.Format("Score : {0}", i)`**

| 생기는 것 | 왜 | 크기 |
|---|---|---|
| ① 박싱된 `int` 상자 | `Format`이 인자를 `object`로 받아서 | 20 B ([1편](boxing-dictionary.md)에서 잰 값) |
| ② 결과 `"Score : 5999"` | 우리가 원한 것 | 46 B |
| **합계** | | **66 B** |

**1·4번 — `"Score : " + i`, `StringBuilder.Append(i)`**

| 생기는 것 | 왜 | 크기 |
|---|---|---|
| ① 숫자 문자열 `"5999"` | 숫자를 먼저 문자열로 바꾼 뒤에 붙여서 | 22 + 4 × 2 = 30 B |
| ② 결과 `"Score : 5999"` | 우리가 원한 것 | 46 B |
| **합계** | | **76 B** |

- ②는 두 방식이 똑같다. **다른 건 ①, 숫자를 넘기는 방식**뿐이다
  - 2·3번은 숫자를 상자에 담아 넘긴다 → 상자 20 B
  - 1·4번은 숫자를 문자열로 바꿔서 넘긴다 → 문자열 30 B

### 측정값과 맞춰 보기 (평균)

실험은 `i`를 0~5999까지 돌렸으니 글자 수가 매번 다르다. 평균을 내면:

| | 평균 글자 수 | 크기 |
|---|---|---|
| 결과 문자열 (`"Score : "` 8자 + 숫자) | 11.8자 | 22 + 23.6 = 45.6 B |
| 숫자 문자열 (1·4번의 ①) | 3.8자리 | 22 + 7.6 = 29.6 B |

| 케이스 | ① | ② | 계산 | 측정 |
|---|---|---|---|---|
| 2·3번 | 박싱 20 | 45.6 | 65.6 B | 65.6 B ✅ |
| 1·4번 | 숫자 문자열 29.6 | 45.6 | 75.2 B | 75.3 B ✅ |

- 5번: 값이 0~99라 결과 평균 9.9자 → 67.6 B × 100개 = 6,760 B = 6.6 KB. 글자가 짧아진 만큼 개당 크기도 작아서 감소폭이 정확히 60배가 아니라 66.8배

## 4. 알아낸 것

### 박싱을 안 하는 방식이 메모리를 더 썼다

비교한 네 줄 (실험 코드 그대로, 전체 코드: [StringGC.cs](https://github.com/DEV-JSB/unity-study/blob/main/Assets/Chapter/02.StringGC/StringGC.cs)):

```csharp
// 박싱하는 방식 — 숫자 i가 object 인자로 넘어감
_str = $"Score : {i}";                                       // 2번
_str = string.Format("Score : {0}", i);                      // 3번

// 박싱 안 하는 방식 — 숫자 i를 먼저 문자열로 바꿔서 붙임
_str = "Score : " + i;                                       // 1번
_builder.Clear();
_str = _builder.Append("Score : ").Append(i).ToString();     // 4번
```

| | 박싱하는 방식 (2·3번) | 박싱 안 하는 방식 (1·4번) |
|---|---|---|
| 숫자를 어떻게 넣나 | 숫자를 상자에 담아 넘기고, 결과 문자열에 자릿수를 바로 써넣음 | 숫자를 먼저 `"5999"` 같은 문자열로 바꾼 뒤 붙임 |
| 결과 문자열 말고 더 생기는 것 | 박싱 상자 20 B | 숫자 문자열 약 30 B |
| 문자열 1개 만들 때 쓴 메모리 | **65.6 B** | 75.3 B (15% 더 큼) |

- **"박싱을 피했다" ≠ "메모리를 덜 쓴다".** 1편만 하고 나면 박싱만 없애면 된다고 생각하기 쉬운데, 박싱은 여러 비용 중 하나일 뿐이다. 박싱을 없애는 대신 다른 걸(숫자 문자열) 만들면 오히려 더 쓸 수 있다

### `$""`는 컴파일되면 `string.Format`과 똑같아진다

- 2번(`$"Score : {i}"`)과 3번(`string.Format("Score : {0}", i)`)이 **384.6 KB로 소수점까지 똑같았다**
- "비슷하다"면 아무것도 알 수 없지만, "정확히 같다"는 **두 줄이 같은 코드로 컴파일됐다**는 뜻이다. 즉 컴파일러가 `$"Score : {i}"`를 `string.Format("Score : {0}", i)`로 바꿔 넣는다. 측정으로 컴파일러 동작을 알아낸 것
- 주의 (공식 문서): Unity가 쓰는 C# 9 기준이다. C# 10 + .NET 6 이상에서는 `$""`가 `DefaultInterpolatedStringHandler`로 바뀌어 박싱 없이 만들어진다. Unity가 그 버전으로 올라가면 다시 재 볼 것

### StringBuilder는 "조각 2개를 한 번 붙이고 끝"일 때는 이점이 없다

이 실험의 4번 코드는 이렇다. `"Score : "`와 숫자, **조각 2개를 한 번 붙이고 바로 결과를 꺼낸다.**

```csharp
_builder.Clear();
_str = _builder.Append("Score : ").Append(i).ToString();
```

결과는 1번(`"Score : " + i`)과 똑같이 441.0 KB. 아낀 게 하나도 없다. 이유는 둘:

1. **StringBuilder가 아껴 주는 건 "이어 붙이는 도중에 생기는 문자열"이다.** 그런데 조각이 2개면 `+`도 도중에 생기는 문자열이 없다 (컴파일러가 `string.Concat` 한 번으로 바꿔 줌). 아낄 게 처음부터 없었다
2. **마지막 `ToString()`이 결과 문자열을 어차피 만든다.** StringBuilder 안의 버퍼는 `char[]`라서, `string`이 필요하면 새로 만들어야 한다

StringBuilder가 이기는 건 **루프를 돌면서 계속 이어 붙일 때**다 (이번엔 측정 안 함, 커뮤니티 표준):

```csharp
// + 로 누적: 돌 때마다 점점 긴 새 문자열이 생긴다
string s = "";
for (int k = 0; k < 5; ++k) s += k;     // "0", "01", "012", "0123", "01234" → 5개 생김

// StringBuilder로 누적: 버퍼 하나에 계속 써넣고 마지막에 1개만
var sb = new StringBuilder();
for (int k = 0; k < 5; ++k) sb.Append(k);
string s2 = sb.ToString();              // "01234" → 1개
```

| 이렇게 붙일 때 | 고를 것 |
|---|---|
| 한 줄에서 조각 2~3개 (`"HP: " + hp`) | `+` 또는 `$""` — 어차피 `Concat` 한 번 |
| 루프를 돌며 계속 이어 붙임 (로그 여러 줄, 목록 출력) | `StringBuilder` |

- 기준은 **"얼마나 자주 만드나"가 아니라 "한 문자열을 만들 때 몇 번에 걸쳐 붙이나"**

### `+`가 박싱 안 하는 걸 어떻게 확인했나

- `string.Format(string, object)`는 **시그니처만 봐도** 박싱 확정 (인자가 `object`)
- `+`는 연산자라 **소스에 메서드 이름이 없다** → 컴파일러가 `string.Concat` 오버로드 중 뭘 골랐는지 코드에서 안 보인다
- 그래서 **박싱이 절대 일어날 수 없는 형태**로 바꿔서 쟀다

```csharp
_str = "Score : " + i.ToString();   // 직접 문자열로 바꿔서 넘김 → 박싱 불가능
```

- 결과 441.0 KB = 1번과 같음 → 1번도 원래 `ToString()`으로 바꾼 뒤 문자열끼리 붙이고 있었다 (박싱 없음)
- 일반화: **시그니처로 판단이 안 되면, 의심 요소를 없앤 버전을 만들어 숫자가 같은지 본다**

### 어떤 방법으로 만드느냐보다, 안 만들어도 되는 프레임에 안 만드는 게 훨씬 크다

1~4번과 5번의 차이는 "만드는 방법"이 아니라 **"몇 번 만드느냐"** 다.

| | 한 프레임에 도는 횟수 | 그중 문자열을 만드는 횟수 | 프레임당 메모리 |
|---|---|---|---|
| 1~4번 (방법만 다름) | 6,000번 | **6,000번** (매번) | 384.6 ~ 441.0 KB |
| 5번 | 6,000번 | **100번** (값이 바뀔 때만) | 6.6 KB |

- 1~4번끼리는 방법을 아무리 바꿔도 차이가 **최대 15%**
- 5번은 만드는 방법은 1번과 같은 `+`인데, 만드는 횟수를 줄여서 **66배** 줄었다

5번 코드 — 직전에 만든 값을 기억해 두고, 값이 그대로면 건너뛴다:

```csharp
int value = i / 60;              // 60번 돌 때마다 1씩 바뀌는 값 (0~99)
if (value != _lastValue)         // 직전과 같으면 문자열을 만들지 않음
{
    _str = "Score : " + value;
    _lastValue = value;
}
```

실전에서는 UI가 이 모양이다. 체력 표시를 `Update()`에서 매 프레임 `hpText.text = "HP: " + hp;`로 갱신하면, 체력이 그대로여도 매 프레임 새 문자열이 생긴다. 화면 글자는 똑같은데 GC 쓰레기만 쌓인다. 체력이 바뀐 프레임에만 갱신하면 된다.

## 5. 결론 — 판단 순서

**박싱은 방법에 따라 생기기도 안 생기기도 하지만, 문자열을 하나 만들면 그 문자열만큼의 힙 할당은 반드시 생긴다.** (결과 문자열 45.6 B는 어떤 방법이든 남음) 그래서 방법을 바꿔서 줄일 수 있는 건 최대 15%다.

1. **값이 바뀐 프레임에만 문자열을 만든다** — 이번 실험에서 66배. 대부분 여기서 끝난다
2. **만들어야 하면 읽기 좋은 방법을 쓴다** — 방법끼리 차이는 최대 15%라 가독성을 버릴 이유가 없다. `$""`가 제일 읽기 쉽고 측정상 제일 작기도 했다 (취향 · 바꿔도 됨)
3. **루프를 돌며 이어 붙일 때만 `StringBuilder`**

## 6. 재지 않았지만 알아둘 것

이번 측정표와 구분한다.

- **TextMeshPro `SetText("HP: {0}", currentHp)`** (공식 문서) — 포맷은 리터럴, 숫자는 TMP 내부 `char[]`에 직접 씀, 인자는 `float`이라 박싱 없음 → **문자열 객체가 0개**
- **`SetText(StringBuilder)`** — `ToString()` 없이 문자를 직접 읽어 감 → 4번에서 마지막 `ToString()`이 만들던 결과 문자열까지 안 생김
- **`Debug.Log`** — 위 비용 + 파일 I/O + **스택 트레이스 문자열**(이게 제일 큼). 빌드에도 남으니 매 프레임 코드엔 넣지 말고 조건부 컴파일(`[Conditional]`)도 고려 (커뮤니티 표준)
