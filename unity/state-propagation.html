상태 전파 — event, static, ReactiveProperty

같은 요구사항(점수가 바뀌면 전광판과 관중이 각자 반응)을 다섯 구조로 만들어 비교한 기록. 한 줄 결론: 통지(event ↔ ReactiveProperty)와 접근(static ↔ 인스턴스 ↔ SO)은 별개의 축이다. UniRx는 통지만 풀어 준다.

글 버전 state-propagation.md · 실습 원본 unity-study / 03.StatePropagation

발단

SkinIndex가 바뀌면 초상화와 SD 프리뷰가 따라 바뀌어야 했습니다. UI_Skin에 SkinIndex를 두고 이벤트를 붙였더니 조언이 왔습니다.

앞으로 다른 로직도 인덱스에 따라 움직일 텐데, 계속 물고 늘어지면 UI_Skin이 너무 무거워진다. 그럴 때 쓰는 게 UniRx다.
점수가 바뀌면 각자 알아서 인지해야지, 전광판이 관중 한 명 한 명에게 일일이 알려주러 다니는 건 좋은 구조가 아니다.

그래서 야구 전광판을 소재로 다섯 구조를 만들었습니다. 실무에서 쓰던 static 방식도 넣었습니다.

비교 기준: 1·2편은 Profiler 숫자가 심판이었지만 설계엔 그런 심판이 없습니다. 그래서 "관중을 한 명 더 붙일 때 손대야 하는 곳이 몇 군데인가"로 봤습니다. (취향 · 바꿔도 됨)

1 · 다섯 구조 — 누가 누구를 아나

안다 (참조 방향)알린다 (값이 바뀌면)

아래 코드는 실습 코드에서 삼성 점수 부분만 남겼습니다. 한화 점수도 똑같은 코드라 생략.

전광판 (ElectronicDisplayBoard1.cs) — 점수, 이벤트, 관중 목록, 입력을 전부 가짐

private int _team1Score;
public event Action<ETeam, int> OnTeam1ScoreChanged;
[SerializeField] private List<Tourist1> _tourist;     // 관중 목록을 인스펙터에서 채움

private void Start()
{
    foreach (var tourist in _tourist)
        tourist.Init(this);                           // 전광판이 관중을 하나씩 등록시켜 줌
}

private void Update()
{
    if (Input.GetKeyDown(KeyCode.S))                  // 입력도 전광판이 받음
    {
        ++_team1Score;
        if (OnTeam1ScoreChanged != null)
            OnTeam1ScoreChanged.Invoke(ETeam.Samsung, _team1Score);
    }
}

관중 (Tourist1.cs) — 전광판이 Init을 불러 줘야만 구독된다

private ElectronicDisplayBoard1 _board;

public void Init(ElectronicDisplayBoard1 board)       // 스스로 구독하지 못하고 불려지기를 기다림
{
    _board = board;
    board.OnTeam1ScoreChanged += OnTeamScoreChanged;
}

private void OnDestroy()
{
    if (_board == null) return;
    _board.OnTeam1ScoreChanged -= OnTeamScoreChanged;
}

시스템 (ScoreSystem.cs) — static 클래스. 씬에 놓을 필요가 없다

public static class ScoreSystem
{
    private static int _team1Score = 0;
    public static event Action<ETeam, int> OnTeam1ScoreChanged;

    public static void AddTeamScore(ETeam team, int score)
    {
        _team1Score += score;
        if (OnTeam1ScoreChanged != null)
            OnTeam1ScoreChanged.Invoke(ETeam.Samsung, _team1Score);
    }
}

점수 넣는 쪽 (ScoreJudgment.cs) — 참조 없이 클래스 이름으로 바로 부름

if (Input.GetKeyDown(KeyCode.S))
    ScoreSystem.AddTeamScore(ETeam.Samsung, 1);

관중 (Tourist2.cs) — 참조 변수가 없다. 클래스 이름으로 바로 구독

private void Start()     { ScoreSystem.OnTeam1ScoreChanged += OnTeamScoreChanged; }
private void OnDestroy() { ScoreSystem.OnTeam1ScoreChanged -= OnTeamScoreChanged; }

시스템 (NonStaticScoreSystem.cs) — 씬 오브젝트에 붙이는 MonoBehaviour. static이 하나도 없다

public class NonStaticScoreSystem : MonoBehaviour
{
    private int _team1Score = 0;
    public event Action<ETeam, int> OnTeam1ScoreChanged;

    public void AddTeamScore(ETeam team, int score)
    {
        _team1Score += score;
        if (OnTeam1ScoreChanged != null)
            OnTeam1ScoreChanged.Invoke(ETeam.Samsung, _team1Score);
    }
}

관중 (Tourist3.cs) — 인스펙터에서 씬의 시스템 오브젝트를 끌어다 꽂아 둔 변수로 구독

[SerializeField] private NonStaticScoreSystem _system;   // 2번엔 없던 줄

private void Start() { _system.OnTeam1ScoreChanged += OnTeamScoreChanged; }   // ScoreSystem. → _system.

private void OnDestroy()
{
    if (_system == null) return;
    _system.OnTeam1ScoreChanged -= OnTeamScoreChanged;
}

점수 넣는 쪽은 실습 코드에 없습니다 (ScoreJudgment는 2번의 static ScoreSystem만 부름). 넣는다면 이쪽도 [SerializeField] NonStaticScoreSystem _system;을 받아 _system.AddTeamScore(...)를 불러야 해요.

시스템 (NonStaticScoreSystem2.cs) — 3번과 같은 MonoBehaviour. event 대신 ReactiveProperty

private readonly ReactiveProperty<int> _samsungScore = new ReactiveProperty<int>();
public IReadOnlyReactiveProperty<int> SamsungScore => _samsungScore;   // 밖에선 읽기·구독만

public void AddScore(ETeam team, int score)
{
    _samsungScore.Value += score;    // 값만 바꾸면 알림은 알아서 간다
}

private void OnDestroy() { _samsungScore.Dispose(); }

관중 (Tourist4.cs) — 참조 받는 법은 3번과 같다. 구독·해제만 바뀜

[SerializeField] private NonStaticScoreSystem2 _system;   // 3번과 같음

private void Start()
{
    _system.SamsungScore
        .Subscribe(score => OnTeamScoreChanged(ETeam.Samsung, score))
        .AddTo(this);                // 이 오브젝트가 파괴되면 구독도 끊김
}
// OnDestroy가 없다 — AddTo(this)가 대신 해 준다

시스템 (ReactiveScoreSystemAsset.cs) — ScriptableObject. 프로젝트 창에서 .asset 파일로 만든다

[CreateAssetMenu(fileName = "ScoreSystem", menuName = "Study/ScoreSystem")]
public class ReactiveScoreSystemAsset : ScriptableObject
{
    private ReactiveProperty<int> _samsungScore;
    public IReadOnlyReactiveProperty<int> SamsungScore => _samsungScore;

    private void OnEnable()          // 필드 초기화 대신 여기서 만든다 → 플레이마다 0부터
    {
        _samsungScore = new ReactiveProperty<int>(0);
    }

    private void OnDisable()
    {
        if (_samsungScore != null) _samsungScore.Dispose();
    }

    public void AddScore(ETeam team, int score) { _samsungScore.Value += score; }
}

관중 (Tourist5.cs) — 4번과 글자까지 거의 같다. 꽂는 대상이 씬 오브젝트가 아니라 .asset 파일

[SerializeField] private ReactiveScoreSystemAsset _system;   // 4번과 다른 건 이 타입 하나

private void Start()
{
    _system.SamsungScore
        .Subscribe(score => OnTeamScoreChanged(ETeam.Samsung, score))
        .AddTo(this);
}

관중을 프리팹으로 만들어도 이 칸에 .asset을 미리 꽂아 둘 수 있어요 (프리팹은 씬 오브젝트를 참조할 수 없음). 점수 넣는 쪽은 3번처럼 실습 코드에 없습니다.

2 · 2~5번은 그림이 같다 — 코드에서 어디가 다른가

화살표 방향(관중 → 시스템)은 2~5번이 모두 같습니다. 다른 건 아래 네 칸 중 어느 칸이냐예요. 한 번에 한 칸씩만 바뀝니다.

시스템 선언관중이 시스템을 찾는 법구독구독 해제
2번public static class ScoreSystem변수 없음. 클래스 이름으로 바로 ScoreSystem.ScoreSystem.OnTeam1ScoreChanged += …OnDestroy에서 -=
3번public class NonStaticScoreSystem : MonoBehaviour[SerializeField] 변수에 씬의 시스템 오브젝트를 끌어다 꽂음_system.OnTeam1ScoreChanged += …OnDestroy에서 -=
4번3번과 같음 (event → ReactiveProperty)3번과 같음_system.SamsungScore.Subscribe(…).AddTo(this) — OnDestroy 없음
5번public class ReactiveScoreSystemAsset : ScriptableObject[SerializeField] 변수에 프로젝트 창의 .asset 파일을 끌어다 꽂음4번과 같음4번과 같음
  • 2 → 3: 찾는 법이 바뀜 (클래스 이름 → 참조 변수)
  • 3 → 4: 구독·해제가 바뀜 (+= / -= → Subscribe / AddTo)
  • 4 → 5: 시스템이 사는 곳이 바뀜 (씬 오브젝트 → 에셋 파일)

3 · UniRx를 얹으면 사라지는 것 (3번 → 4번)

3번에서 통지만 바꿨습니다. 한 번에 하나만 바꿔야 차이가 UniRx 몫인지 압니다.

// 시스템
private readonly ReactiveProperty<int> _samsungScore = new ReactiveProperty<int>();
public IReadOnlyReactiveProperty<int> SamsungScore => _samsungScore;   // 밖에선 읽기만
public void AddScore(int score) => _samsungScore.Value += score;        // 바뀌면 알아서 알림

// 구독자
_system.SamsungScore.Subscribe(s => OnScoreChanged(s)).AddTo(this);   // 내가 파괴되면 자동 해제
event (3번)ReactiveProperty (4번)
Action 따로 선언필요 없음
if (Event != null) Event.Invoke(...).Value += score; 한 줄
구독자마다 OnDestroy에서 -=AddTo(this)로 통째로 사라짐
밖에서 값 변경을 막으려면 직접 설계IReadOnlyReactiveProperty로 내보내면 끝
구독해도 다음 득점 전까진 점수를 모름 → 첫 득점 전 빈 화면Subscribe 순간 현재값이 즉시 한 번 들어옴

처음엔 둘을 하나로 보고 "UniRx를 쓰면 둘 다 해결"이라고 오해했습니다.

  • UniRx는 통지를 간편·안전하게 해 줄 뿐, 상태를 어디 둘지는 여전히 내가 정한다
  • UI_Skin이 무거워진 원인은 UI가 상태를 소유한 것이었고, 그건 이미 2번(상태 분리)에서 풀렸다. UniRx는 그 위의 편의
  • 빈 칸(static + ReactiveProperty 등)은 이번에 안 만든 조합일 뿐, 못 만드는 게 아니다

결론 — 이런 상황엔 이걸

UniRx 구독은 매우 편했고 앞으로 기본으로 깔고 가고 싶습니다 (취향 · 바꿔도 됨). 하지만 의존성과 책임을 어떻게 나눌지는 UniRx가 답해 주지 않습니다. 생명주기, 필요한 개수, 프리팹 여부로 정합니다. 정답 하나가 아니라 판단만 남습니다.

이런 상황이면먼저 떠올릴 것
하나뿐이고, 씬과 무관하게 살아도 되고, 참조 전달이 귀찮다static (리셋 책임을 같이 짊어짐)
씬 안에서만 살고 씬과 같이 사라져야 한다인스턴스 + 참조
여러 벌이 필요하거나, 런타임 생성 프리팹이 구독해야 한다ScriptableObject
어떤 경우든 "바뀌면 알려줘"가 필요하다ReactiveProperty (통지 축은 따로 고름)
