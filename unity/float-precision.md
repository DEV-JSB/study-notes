# 좌표가 커지면 캐릭터가 멈춘다 — float 정밀도

> Unity · C# 런타임 · 2026-11-10 — 직접 돌려 보는 그림은 [float-precision.html](float-precision.html)
>
> 실습 원본: [unity-study / 04.FloatPrecision](https://github.com/DEV-JSB/unity-study/tree/main/Assets/Chapter/04.FloatPrecision)

## 발단

실무 프로젝트(TBH)는 캐릭터가 왼쪽에서 오른쪽으로, 좌표 한 축을 따라 계속 이동하는 구조다. 이동은 `float` 속도에 `deltaTime`을 곱해 좌표에 더하는 방식이었다.

스테이지를 옮기거나 재시작하면 좌표를 0으로 되돌리기 때문에, 좌표가 크게 쌓이지 않는다는 전제로 설계했다. 그런데 **같은 스테이지를 반복할 때는 0으로 되돌리는 코드가 없었고**, 게임을 오래 켜 둔 유저에게서 문제가 생겼다.

원인을 따라가 보니 두 가지가 걸려 있었다.

- 좌표(`Transform.position`)는 `float`이라서 **값이 커질수록 표현할 수 있는 간격이 넓어진다**
- 그 상태에서는 **작은 이동값을 더해도 좌표가 변하지 않을 수 있다**

둘 다 이번에 처음 제대로 들여다봤다. 그리고 좌표를 0으로 되돌린다는 전제가 스테이지 반복 경로에서는 성립하지 않았다.

그래서 "좌표가 얼마일 때, 얼마짜리 이동이, 실제로 얼마나 먹히는가"를 직접 재 보고, 왜 그런지 `float`의 구조까지 내려가서 정리했다. 이 노트에는 회사 코드가 없다. 같은 조건을 빈 씬에서 다시 만들어 쟀다.

**한 줄 결론: `float`은 2진수 24자리만 쓸 수 있고, 그 자리를 정수 부분과 소수 부분이 나눠 쓴다. 좌표가 커져 정수 부분이 자리를 많이 차지하면 소수 자리가 모자라서, 작은 이동은 반올림으로 사라진다.**

## 1. 배경 지식 ① — 2진수에도 자릿값이 있다

10진수는 자리가 왼쪽으로 하나 갈 때마다 10배, 소수점 오른쪽으로 하나 갈 때마다 10으로 나눈 값이다.

```
   백   십   일  .  소수 첫째   소수 둘째   소수 셋째
  100   10    1  .    1/10       1/100      1/1000
        ← 10배씩            10으로 나누기 →
```

2진수는 똑같은 줄인데 10 대신 2다.

```
    4    2    1  .  소수 첫째   소수 둘째   소수 셋째   소수 넷째
    4    2    1  .    1/2        1/4        1/8        1/16
        ← 2배씩             2로 나누기 →
```

예: 2진수 `101.11`

```
  1    0    1  .   1     1
  4    2    1  .  1/2   1/4
  4 +  0 +  1  +  0.5 + 0.25  =  5.75
```

- 소수 자리가 n개 있으면, **맨 끝자리 하나의 값은 1을 2로 n번 나눈 값**이다. 그보다 잘게는 표현할 수 없다
- 소수 4자리면 맨 끝자리는 1/16 = 0.0625. 표현할 수 있는 소수 부분은 0, 1/16, 2/16, 3/16, … 뿐이다

## 2. 배경 지식 ② — 2진수로 몇 자리인지 세는 법 (변환하지 않고)

어떤 수가 2진수로 몇 자리인지는 2진수로 바꿔 쓰지 않아도 알 수 있다. 10진수에서 "4,321은 1,000 이상 10,000 미만이니 4자리"라고 하는 것과 같다.

| 2진 자릿수 | 그 자릿수가 되는 수 |
|---|---|
| 1자리 | 1 |
| 2자리 | 2부터 3까지 |
| 3자리 | 4부터 7까지 |
| 4자리 | 8부터 15까지 |
| 5자리 | 16부터 31까지 |

방법은 두 가지고 답은 같다.

- **곱해서 올라가기**: 1, 2, 4, 8, 16, … 으로 2배씩 키우다가, 내 수를 넘기 직전까지 몇 개였는지 센다
- **나눠서 내려가기**: 내 수를 2로 계속 나눠(나머지는 버림) 0이 될 때까지 몇 번 나눴는지 센다

13으로 해 보면:

| 방법 | 과정 | 답 |
|---|---|---|
| 곱해서 올라가기 | 1, 2, 4, 8 (다음 16은 13을 넘음) | 4개 → 4자리 |
| 나눠서 내려가기 | 13 → 6 → 3 → 1 → 0 | 4번 → 4자리 |

실제로 13은 2진수로 `1101`, 4자리다.

좌표에서 자주 만나는 범위:

| 2진 자릿수 | 그 자릿수가 되는 수 |
|---|---|
| 10자리 | 512부터 1,023까지 |
| 17자리 | 65,536부터 131,071까지 |
| 19자리 | 262,144부터 524,287까지 |
| 20자리 | 524,288부터 1,048,575까지 |
| 21자리 | 1,048,576부터 2,097,151까지 |
| 24자리 | 8,388,608부터 16,777,215까지 |

## 3. 배경 지식 ③ — float은 32칸짜리 상자, 숫자에 쓸 수 있는 건 24자리

```
 부호 1칸   지수 8칸        숫자 본체 23칸
┌───┬──────────┬─────────────────────────┐
│ 0 │ 10010010 │ 11101000010010000000000 │   ← 1,000,000
└───┴──────────┴─────────────────────────┘
```

- **숫자 본체**: 2진수로 쓴 숫자의 자릿수들. 23칸이 저장되고, 맨 앞의 1은 항상 1이라 저장을 생략한다. 그래서 실제로 쓸 수 있는 자리는 **24자리** (IEEE 754 표준)
- **지수**: 소수점을 어디에 찍을지. 소수점 위치가 값에 따라 움직여서 "부동(떠다니는) 소수점"이다
- 이 문제를 이해하는 데는 지수의 저장 방식까지는 필요 없다. **"24자리를 정수 부분과 소수 부분이 나눠 쓴다"**만 알면 된다

1,000,000은 2진수로 20자리다 (524,288 이상 1,048,576 미만).

```
11110100001001000000 . _ _ _ _
└──── 정수 20자리 ────┘ └ 소수 4자리 ┘
                        1/2 1/4 1/8 1/16
```

24자리 중 20자리를 정수가 썼으니 소수에는 4자리만 남는다. 맨 끝자리 값은 1/16 = **0.0625**. 1,000,000 근처에서는 0.0625보다 잘게 좌표를 구분할 수 없다.

실제 비트로 보면, 바로 다음 `float`은 본체의 맨 끝자리 하나만 다르다.

```
1,000,000        0 | 10010010 | 11101000010010000000000
1,000,000.0625   0 | 10010010 | 11101000010010000000001   ← 끝자리 +1
```

## 4. 눈금 간격 — 좌표가 2배 커지면 간격도 2배

이웃한 두 `float` 사이의 거리를 이 노트에서는 **눈금 간격**이라고 부른다. 구하는 순서는 세 단계다.

| 단계 | 할 일 | 1,000,000이면 |
|---|---|---|
| 1 | 정수 부분이 2진수로 몇 자리인지 센다 (2절) | 20자리 |
| 2 | 24에서 뺀다 → 소수에 남는 자리 | 24 − 20 = 4자리 |
| 3 | 1을 2로 그 횟수만큼 나눈다 → 눈금 간격 | 1 → 1/2 → 1/4 → 1/8 → 1/16 = 0.0625 |

| 좌표 | 정수 부분 2진 자릿수 | 소수에 남는 자리 | 눈금 간격 |
|---|---|---|---|
| 1 | 1 | 23 | 0.00000012 |
| 1,000 | 10 | 14 | 0.000061 |
| 100,000 | 17 | 7 | 0.0078125 |
| 300,000 | 19 | 5 | 0.03125 |
| 1,000,000 | 20 | 4 | 0.0625 |
| 2,000,000 | 21 | 3 | 0.125 |
| 9,999,999 | 24 | 0 | 1 |
| 16,777,216 | 25 | 모자람 | 2 (홀수는 표현 못 함) |

- 좌표가 2배가 되면 정수 부분이 한 자리 늘고, 소수 자리가 하나 줄어서, **눈금 간격이 2배**가 된다
- 0에 가까울수록 눈금이 촘촘하고, 멀어질수록 성겨진다

## 5. 더한 결과는 가장 가까운 눈금으로 간다

`float` 덧셈의 결과가 눈금 사이에 떨어지면 **가장 가까운 눈금으로 반올림**된다 (IEEE 754 표준의 기본 방식). `Mathf.RoundToInt`와 같은 원리다. `RoundToInt`는 눈금 간격이 1인 자이고, `float`은 눈금 간격이 좌표에 따라 달라지는 자다.

```
RoundToInt (눈금 간격 1)                가장 가까운 눈금
0 ─────────┼───────── 1
     0.4   │                          → 0
           │   0.6                    → 1
         절반 0.5

x = 1,000,000 (눈금 간격 0.0625)
1,000,000 ───────┼─────── 1,000,000.0625
         +0.02   │                    → 1,000,000        (제자리)
                 │  +0.04             → 1,000,000.0625   (한 칸 감)
            절반 0.03125
```

- 더하는 값이 **눈금 간격의 절반보다 작으면** 원래 눈금이 더 가까워서 제자리로 돌아온다. 이동이 사라진다
- 절반보다 크면 다음 눈금으로 간다. 이때 더한 값이 얼마든 **눈금 한 칸**만큼 간다

```csharp
float x = 1_000_000f;   // 눈금 간격 0.0625
x += 0.02f;             // 0.32칸 → 0칸으로 반올림. x는 그대로 1,000,000
x += 0.04f;             // 0.64칸 → 1칸으로 반올림. x는 1,000,000.0625 (0.04를 더했는데 0.0625가 늘었다)
```

## 6. 초당 속도로 바꿔 보기 — 60프레임 기준

Speed는 **1초에** 가는 거리이고, 사라지는지는 **한 프레임에** 더하는 값으로 정해진다. 60프레임이면 이렇게 오간다.

```
한 프레임에 더하는 값 = Speed ÷ 60
1초에 실제로 간 거리  = 한 프레임에 실제로 간 거리 × 60
```

x = 1,000,000 (눈금 간격 0.0625)에서:

| 넣은 Speed (초당) | 한 프레임에 더하는 값 (÷ 60) | 눈금으로 몇 칸 (÷ 0.0625) | 반올림 | 한 프레임에 실제로 간 거리 | 1초에 실제로 간 거리 (× 60) |
|---|---|---|---|---|---|
| 1.00 | 0.0167 | 0.27칸 | 0칸 | 0 | **0** |
| 1.85 | 0.0308 | 0.49칸 | 0칸 | 0 | **0** |
| 1.89 | 0.0315 | 0.50칸을 조금 넘음 | 1칸 | 0.0625 | **3.75** |
| 3.00 | 0.05 | 0.8칸 | 1칸 | 0.0625 | **3.75** |

- 멈춤과 움직임의 경계: 한 프레임에 0.03125 (간격의 절반) → Speed로는 0.03125 × 60 = **1.875**
- 움직이면 한 프레임에 한 칸(0.0625)씩 → 0.0625 × 60 = **초당 3.75**. Speed 1.89든 3.0이든 같다
- 즉 이 좌표에서 낼 수 있는 속도는 0, 3.75, 7.5, … 뿐이다. 그 사이의 속도는 존재하지 않는다

좌표별 경계 (60프레임):

| 좌표 | 눈금 간격 | 이 Speed를 넘어야 움직인다 (간격의 절반 × 60) | 움직일 때 최소 속도 (간격 × 60) |
|---|---|---|---|
| 1,000,000 | 0.0625 | 1.875 | 초당 3.75 |
| 2,000,000 | 0.125 | 3.75 | 초당 7.5 |
| 9,999,999 | 1 | 30 | 초당 60 |

## 7. Unity에서 직접 잰 결과

Unity 6000.0.72f1 · 에디터 · 빈 씬에 부모 없는 오브젝트 하나 · 매 프레임 1/60초로 고정해서 이동 · 60프레임마다 요약을 Console에 출력

재는 방법: 더하려던 값과 실제로 늘어난 좌표를 나란히 비교한다. ([FloatPrecision.cs](https://github.com/DEV-JSB/unity-study/blob/main/Assets/Chapter/04.FloatPrecision/FloatPrecision.cs))

```csharp
float requested = _speed * deltaTime;               // 더하려던 이동량

float before = transform.position.x;
transform.position += new Vector3(requested, 0f, 0f);
float after = transform.position.x;

float actual = after - before;                      // 실제로 늘어난 좌표
```

눈금 간격은 `float`의 비트를 정수로 꺼내 1을 더해서 구했다. 3절의 "본체 맨 끝자리 +1"을 코드로 한 것이다.

```csharp
float next = BitConverter.Int32BitsToSingle(BitConverter.SingleToInt32Bits(abs) + 1);
return next - abs;   // 바로 다음 float까지의 거리
```

### Speed 3 (한 프레임에 0.05)을 좌표만 바꿔 가며

| 좌표 | 눈금 간격 | 1초에 실제로 간 거리 | 의도(3.0) 대비 | 출처 |
|---|---|---|---|---|
| 0 근처 | 0.0000002부터 0.000015까지 | 3.000 | 100% | Unity 측정 |
| 1,000 | 0.000061 | 2.9993 | 99.98% | PC 계산 |
| 100,000 | 0.0078125 | 2.8125 | 93.75% (느려짐) | PC 계산 |
| 300,000 | 0.03125 | 3.75 | 125% (빨라짐) | PC 계산 |
| 1,000,000 | 0.0625 | 3.75 | 125% (빨라짐) | Unity 측정 |
| 1,082,766 | 0.125 | 0 | 0% (멈춤) | Unity 측정 |
| 9,999,999 | 1 | 0 | 0% (멈춤) | Unity 측정 |

- "PC 계산"은 Unity가 아니라 같은 `float` 덧셈을 PC에서 60번 돌린 값이다. Unity 측정값과 같은 줄(0 근처, 1,000,000)에서 숫자가 일치하는 것을 확인했다
- **멈추기 전에 먼저 속도가 틀어진다.** 100,000에서는 6% 느리고, 300,000부터 1,000,000까지는 25% 빠르다. 눈금 6.4칸이 6칸으로, 0.8칸이 1칸으로 반올림되기 때문이다
- 1,048,576을 넘으면 눈금 간격이 0.125가 되고, 0.05는 0.4칸이라 0칸으로 반올림된다. 완전히 멈춘다

### 좌표를 고정하고 Speed만 바꿔 가며

Play 중에 Inspector에서 Speed를 조금씩 바꿨다.

재기 전에 6절의 방법으로 **"이 Speed보다 크면 움직이고, 작으면 멈춘다"는 값을 먼저 계산**해 두었다. 아래에서는 이 값을 "예상한 경계 Speed"라고 부른다.

```
예상한 경계 Speed = 눈금 간격의 절반 × 60

눈금 간격 0.0625  →  0.03125 × 60 = 1.875
눈금 간격 0.125   →  0.0625  × 60 = 3.75
눈금 간격 1       →  0.5     × 60 = 30
```

측정에서 볼 것은 하나다. **실제로 이 값을 사이에 두고 멈춤과 움직임이 갈리는가.**

좌표 약 1,000,000 (눈금 간격 0.0625) — 예상한 경계 Speed 1.875 (이보다 크면 움직여야 한다)

| 넣은 Speed | 1초에 실제로 간 거리 | 안 움직인 프레임 (60 중) |
|---|---|---|
| 1.00 | 0 | 60 |
| 1.68 | 0 | 60 |
| 1.83 | 0 | 60 |
| 1.85 | 0 | 60 |
| 1.89 | 3.75 | 0 |
| 2.15 | 3.75 | 0 |
| 3.00 | 3.75 | 0 |

좌표 약 1,080,000 (눈금 간격 0.125) — 예상한 경계 Speed 3.75

| 넣은 Speed | 1초에 실제로 간 거리 | 안 움직인 프레임 (60 중) |
|---|---|---|
| 1.00 | 0 | 60 |
| 3.25 | 0 | 60 |
| 3.68 | 0 | 60 |
| 3.72 | 0 | 60 |
| 3.83 | 7.5 | 0 |
| 3.89 | 7.5 | 0 |
| 5.34 | 7.5 | 0 |

좌표 9,999,999 (눈금 간격 1) — 예상한 경계 Speed 30

| 넣은 Speed | 1초에 실제로 간 거리 | 안 움직인 프레임 (60 중) |
|---|---|---|
| 3.00 | 0 | 60 |
| 4.17 | 0 | 60 |
| 5.53 | 0 | 60 |

- 이 좌표에서는 Speed를 3에서 5.53 사이로만 바꿔 봤다 (표의 세 값은 그중 일부). 전부 예상한 경계 30보다 훨씬 작고, 전부 멈췄다
- **30을 넘는 Speed는 재지 않았다.** 그래서 이 좌표에서는 "경계 아래에서 멈춘다"만 확인했고, "30을 넘으면 움직인다"는 확인하지 못했다

정리하면:

- 앞의 두 좌표는 **예상한 경계 Speed를 사이에 두고 정확히 갈렸다.** 1.875 아래인 1.85는 멈추고 위인 1.89는 간다. 3.75 아래인 3.72는 멈추고 위인 3.83은 간다
- 9,999,999는 경계 아래쪽만 확인했다
- 움직일 때의 속도도 계산한 값(눈금 간격 × 60)과 같은 3.75, 7.5였다. 넣은 Speed와 상관없다

## 8. 화면도 같이 깨진다

좌표를 1,000,000으로 두면 이동만 틀어지는 게 아니라 **물체가 제대로 그려지지 않는다.** 씬뷰에서 3D 물체가 일그러지고 떨리는 것을 직접 봤다.

원인은 같다. 물체는 점(정점, vertex)들을 이어 붙인 것이고, 그 점의 좌표도 `float`이다 (엔진 표준). 점마다 따로 눈금에 반올림된다.

```
점의 월드 좌표 = 물체의 좌표 + 물체 안에서의 위치     (설명용으로 줄인 식)
```

지름 1짜리 Sphere를 x = 1,000,000 (눈금 간격 0.0625)에 놓으면:

| 점의 물체 안 위치 | 원래 가야 할 곳 | 실제로 놓이는 곳 (가장 가까운 눈금) | 밀린 거리 |
|---|---|---|---|
| 0.10 | 1,000,000.10 | 1,000,000.125 | 0.025 |
| 0.31 | 1,000,000.31 | 1,000,000.3125 | 0.0025 |
| 0.40 | 1,000,000.40 | 1,000,000.375 | 0.025 |
| 0.47 | 1,000,000.47 | 1,000,000.50 | 0.03 |

- 점마다 **밀리는 양이 다 다르다.** 물체 전체가 같이 밀리면 위치만 틀릴 텐데, 따로 밀려서 모양이 일그러진다
- 지름 1은 눈금으로 16칸이다. 매끈한 곡면을 16칸짜리 계단으로 그리는 셈
- 스프라이트도 같다. 점이 4개인 사각형이라, 사각형이 프레임마다 조금씩 다른 크기로 그려지고 그 위의 픽셀이 늘어나 보인다

| 좌표를 쓰는 곳 | 눈금이 성기면 생기는 일 |
|---|---|
| 이동 코드 (`position += …`) | 작은 이동이 사라지거나, 한 칸씩만 가서 속도가 틀어짐 |
| 3D 메시의 정점 | 모양이 일그러지고 떨림 |
| 2D 스프라이트의 네 꼭짓점 | 픽셀이 늘어나거나 찌그러져 보임 |
| 카메라 위치 | 눈금 단위로 끊겨 움직여서 화면 전체가 떨림 |

## 9. 같은 문제가 숨어 있는 다른 곳 — 시간 누적

좌표만의 문제가 아니다. **`float`에 작은 값을 계속 더해 가는 모든 변수**가 같은 길을 간다.

```csharp
private float _playTime;

private void Update()
{
    _playTime += Time.deltaTime;   // 60프레임이면 한 프레임에 약 0.0167
}
```

| `_playTime` | 눈금 간격 | 0.0167을 더하면 | 일어나는 일 |
|---|---|---|---|
| 262,144초 전까지 (약 3일 전까지) | 0.015625 이하 | 1칸 이상 | 조금씩 틀어지지만 거의 정상 |
| 262,144초부터 524,288초 전까지 (약 3일부터 6일까지) | 0.03125 | 0.53칸 → 1칸 = 0.03125 | 시간이 약 1.9배 빨리 감 |
| 524,288초부터 (약 6일) | 0.0625 | 0.27칸 → 0칸 | **시간이 멈춤** |

- 하루는 86,400초. 524,288 ÷ 86,400 = 약 6.07일
- 이 표는 계산이다. 직접 6일을 켜 두고 재지는 않았다
- 오버플로우가 아니다. `float`의 최댓값은 0이 38개쯤 붙는 수라서 이런 식으로는 닿지 않는다

## 10. 고치는 방향

이번에 재지는 않았다. 방향만 적어 둔다.

| 방법 | 내용 | 출처 성격 |
|---|---|---|
| 좌표를 주기적으로 0 근처로 되돌린다 | 스테이지 이동·재시작뿐 아니라 **스테이지 반복 때도** 캐릭터와 주변 물체를 함께 원점 쪽으로 옮긴다. 이번 문제의 직접 원인이 이 리셋이 빠진 것이었다 | 커뮤니티 표준 (floating origin) |
| 누적은 `double`로, 넘길 때만 `float`으로 | `double`은 2진수 53자리라 눈금이 훨씬 촘촘하다. 다만 `Transform.position` 자체는 `float`이라 좌표에는 쓸 수 없고, 시간·거리 누적 같은 내 변수에만 쓸 수 있다 | 공식 문서 (C# 자료형) |
| 좌표가 커질 일이 없는 구조로 만든다 | 캐릭터를 움직이지 않고 배경을 움직이는 식 | 취향 · 바꿔도 됨 |

## 정리

- Unity 좌표는 `float`이고, `float`은 2진수 24자리를 정수 부분과 소수 부분이 나눠 쓴다
- 좌표가 2배 커질 때마다 눈금 간격이 2배가 된다. 1,000,000에서 0.0625, 2,000,000에서 0.125
- 더한 결과는 가장 가까운 눈금으로 반올림된다. 한 프레임 이동량이 눈금 간격의 절반보다 작으면 사라진다
- 멈추기 전에 속도가 먼저 틀어지고(느려지거나 빨라짐), 화면도 같이 깨진다
- 0으로 되돌리는 코드가 **모든 경로**에 있는지 확인해야 한다. 한 경로만 빠져도 오래 켜 둔 유저에게서 터진다
