같은 변수를 두 스레드가 더하면 값이 사라진다 — 경쟁 상태와 lock

두 워커 스레드가 같은 _count를 더하는 실험으로 경쟁 상태를 직접 보고, Interlocked · lock · SemaphoreSlim으로 고친 뒤 비용을 잰 기록. 한 줄 결론: _count++는 읽기·더하기·쓰기 세 단계라 겹치면 값이 사라진다. 막는 도구는 공짜가 아니어서 범위와 도구를 목적에 맞게 고른다.

글 버전 race-condition.md · 실습 원본 unity-study / 05.RaceCondition

발단

실무 프로젝트(TBH)의 세이브 저장 코드에 SemaphoreSlim, Interlocked.Exchange, UniTask.RunOnThreadPool을 썼습니다. 그런데 이 부분은 AI에게 맡겨서 짰고, 다시 읽어 보니 왜 이런 모양인지 설명할 수 없었습니다. 동작하는 코드를 갖고 있어도 설명하거나 고칠 수 없으면 내 코드가 아닙니다.

그래서 스레드를 기초부터 다시 공부하기로 했고, 이 노트가 첫 단계입니다. 두 스레드가 같은 변수를 동시에 건드리면 무슨 일이 생기는지, 그걸 막는 도구는 각각 무엇이고 얼마나 비싼지를 빈 씬에서 직접 쟀습니다. 회사 코드는 없습니다.

1 · 용어 먼저

용어뜻
스레드코드를 한 줄씩 실행하는 일꾼 하나. 같은 프로그램 안의 스레드들은 같은 변수를 함께 본다
메인 스레드Unity가 Update, 렌더링, 입력을 처리하는 스레드 1개. 게임 화면 담당
워커 스레드메인 스레드가 아닌, 일을 받아서 처리해 주는 보조 스레드 (업계에서 널리 쓰는 말)
스레드 풀.NET이 워커 스레드를 미리 만들어 두는 대기실. 새로 만드는 비용이 비싸서 재사용한다 (.NET 공식 문서)
Task.Run(일)스레드 풀에서 워커 하나를 빌려서 일을 시킨다. 끝나면 워커는 대기실로 돌아간다. UniTask의 UniTask.RunOnThreadPool과 같은 일

async 메서드를 만든다고 스레드가 생기지는 않습니다. 다른 스레드에서 돌게 하려면 Task.Run으로 넘겨야 합니다.

2 · 실험 1 — 두 스레드가 1만 번씩: 5번 중 2번 값이 사라졌다

private void AddMany()
{
    for (int i = 0; i < _loopCount; ++i)
    {
        _count++;   // 두 워커 스레드가 같은 _count 를 더한다
    }
}

Task workerA = Task.Run(AddMany);
Task workerB = Task.Run(AddMany);
await Task.WhenAll(workerA, workerB);

직접 측정 · Unity 6000.0.72f1 · 에디터(Mono) · 스레드 하나당 1만 번 · 기대값 20,000

돌리기 전 예측은 "20,000이 나오거나, 아니면 프로그램이 터진다"였는데 둘 다 틀렸습니다.

  • 가끔만 틀린다. 1만 번은 너무 빨리 끝나서, 워커 B가 시작하기 전에 워커 A가 끝난 회차는 두 스레드가 아예 겹치지 않았다
  • 틀릴 때는 항상 작다. 기대값보다 커진 회차는 없었다
  • 에러가 나지 않는다. 조용히 틀린 값만 나온다

이렇게 여러 스레드가 같은 것을 동시에 건드려서 결과가 실행 순서에 따라 달라지는 상황을 경쟁 상태(race condition)라고 합니다 (교과서 표준 용어). 세 번 연속 맞으면 "괜찮네" 하고 넘어가게 되는 게 이 버그의 무서운 점입니다.

3 · 왜 사라지나 — _count++ 한 줄은 세 단계

_count++;

// CPU 입장에서는 세 번 나눠서 일한다
int temp = _count;   // ① 읽기
temp = temp + 1;     // ② 더하기
_count = temp;       // ③ 쓰기

++가 한 번에 끝나는 연산(원자적 연산)이 아니라는 것은 .NET 공식 문서의 Interlocked 설명에 나옵니다.

직접 넘겨 보기 — _count가 5일 때 두 워커가 겹치면

순서워커 A워커 B메모리의 _count
1① 읽기 → temp = 55
2① 읽기 → temp = 55
3② 더하기 → temp = 65
4② 더하기 → temp = 65
5③ 쓰기 → 66
6③ 쓰기 → 66 (덮어씀)
  • 항상 작은 이유 — 덮어써서 잃어버리는 일만 생긴다. 한 번에 두 번 더해지는 순서는 없다
  • 안 터지는 이유 — int에 숫자를 쓰는 건 숫자 하나를 쓰는 일이라 깨질 구조가 없다. List.Add를 동시에 하면 예외가 나거나 내부가 망가질 수 있다고 알려져 있다 (이번에 재지는 않음)
  • 가끔 맞는 이유 — 두 스레드가 겹치지 않은 회차에서는 이 순서가 생기지 않는다

4 · 고치는 도구 셋

3절에서 문제가 된 곳은 공유 변수 _count를 건드리는 _count++ 한 줄입니다. 이렇게 여러 스레드가 함께 쓰는 데이터를 건드려서, 한 번에 한 스레드만 들어가야 하는 코드 구간을 임계 구역(critical section)이라고 합니다 (교과서 표준 용어).

그래서 할 일은 두 단계입니다.

  1. 임계 구역을 찾는다. 이번 실험에서는 _count++ 한 줄 (①읽기·②더하기·③쓰기)
  2. 한 번에 한 스레드만 들어가도록 지킨다. 이걸 상호 배제(mutual exclusion)라고 합니다 (교과서 표준 용어)

아래 세 도구는 모두 2번, 임계 구역을 지키는 방법입니다. 흔히 "lock으로 임계 구역을 만든다"고도 말하지만, 정확히는 임계 구역은 공유 데이터를 건드리는 순간 이미 생겨 있고, 도구는 그 구역을 지키는 역할입니다.

Interlocked — CPU에게 세 단계를 한 번에 시킨다

Interlocked.Increment(ref _count);
  • 자물쇠가 없다. CPU에 원래 있는 "한 번에 끝나는 명령"을 쓴다 (.NET 공식 문서)
  • 할 수 있는 일은 변수 하나에 연산 하나뿐이다. _gold를 빼고 _itemCount를 더하는 두 줄이 함께 바뀌어야 하면, 두 줄 사이에 다른 스레드가 끼어들 수 있어 lock이 필요하다

할 수 있는 일은 적지만, 실무에서 자주 쓰이는 곳은 정해져 있습니다.

쓰임코드lock 대신 쓰는 이유
횟수 세기 (처리한 개수, 통계)Interlocked.Increment(ref _count);변수 하나에 1을 더하는 것뿐이라 자물쇠까지 쓸 필요가 없다
고유 번호 발급int id = Interlocked.Increment(ref _nextId);1 더하기와 결과 받기가 한 번에 끝나서 두 스레드가 같은 번호를 받지 않는다. _nextId++; int id = _nextId;로 두 줄에 나눠 쓰면 그 사이에 다른 스레드가 끼어들 수 있다
딱 한 번만 실행if (Interlocked.Exchange(ref _flag, 1) == 0) { ... }Exchange는 _flag를 1로 바꾸고 바꾸기 전 값을 돌려준다. 이게 한 번에 끝나서, 두 스레드가 동시에 와도 0을 돌려받는 스레드는 처음 온 하나뿐이다

TBH 저장 코드는 세 번째 모양으로 "세마포어 반납은 딱 한 번만"을 지켰습니다.

lock — 자물쇠 하나, 쥔 스레드만 들어간다

private readonly object _lock = new();

lock (_lock)        // 이미 누가 쥐고 있으면 여기서 기다린다
{
    _count++;       // ①②③이 통째로 보호된다
}                   // 중괄호를 나가면 자동으로 놓는다
  • 두 스레드가 같은 자물쇠 객체를 써야 의미가 있다
  • 안에서 await를 쓸 수 없다 (컴파일 에러 CS1996, C# 공식 문서)
  • 쥔 스레드가 직접 놓아야 한다. lock은 Monitor.Enter / Monitor.Exit로 컴파일되고, 다른 스레드에서 Monitor.Exit를 부르면 SynchronizationLockException이 난다 (C# 공식 문서)

SemaphoreSlim — 입장권 N장짜리 문

private readonly SemaphoreSlim _semaphore = new(1, 1);   // (처음 입장권 수, 최대 입장권 수)

_semaphore.Wait();          // 입장권 가져가기. 0장이면 기다린다
try
{
    _count++;
}
finally
{
    _semaphore.Release();   // 입장권 돌려주기. 직접 해야 한다
}
생성뜻쓰임
new(1, 1)1장으로 시작, 최대 1장lock과 같은 효과
new(3, 3)3장으로 시작, 최대 3장최대 3개까지 동시에 (예: 동시 다운로드 3개 제한)
new(0, 1)0장으로 시작누가 Release()해 주면 열림 → "준비 끝 신호" 기다리기
  • 최대값을 넘겨 Release()하면 SemaphoreFullException. 두 번 반납하는 버그를 드러내는 안전장치다 (.NET 공식 문서)
  • 누가 쥐었는지 따지지 않고 숫자만 센다. 그래서 메인 스레드가 쥐고 워커 스레드가 반납할 수 있다. 반대로 쥔 적 없는 스레드의 Release()도 막지 않으니 반납 규칙은 직접 지켜야 한다
반납 규칙어기면
가져갔으면 반드시 돌려준다 (try / finally)입장권이 0에 멈춰 이후 전부 영원히 대기
두 번 돌려주지 않는다SemaphoreFullException, 또는 두 스레드가 동시에 들어감
못 가져갔으면 돌려주지 않는다 (Wait는 try 밖에)입장권이 늘어 두 스레드가 동시에 들어감

5 · 잠그는 비용 — 두 스레드가 1,000만 번씩

직접 측정 · Unity 6000.0.72f1 · 에디터(Mono) · 두 스레드 합계 2,000만 번 · 5회 반복 · 막대는 5회 중 대표값

  • for 문 전체를 잠근 쪽이 140배쯤 빨랐다. 한 줄씩 잠그면 자물쇠를 2,000만 번 쥐었다 놓고 그때마다 두 스레드가 다툰다. for 문 전체를 잠그면 자물쇠는 총 2번만 쥔다
  • SemaphoreSlim이 lock보다 3배쯤 느렸다. 내부에서 잠금을 쓰고 그 위에 입장권 숫자 관리를 더 하는 것으로 알고 있다 (.NET 소스를 직접 확인하지는 않음)

비용은 어디서 나오나 — 쥐고 놓기 vs 서로 다투기

스레드를 하나만 써서 한 줄씩 lock을 2,000만 번 걸면, 다툴 상대가 없으니 순수하게 쥐고 놓는 비용만 남습니다. 이 값을 2스레드 결과에서 빼서 나눠 봤습니다.

단계계산값
① 1스레드 + 한 줄씩 lock직접 측정, 5회308–318ms, 약 310ms
② 2스레드 + 한 줄씩 lock직접 측정, 5회약 1,100ms
③ 상대가 생겨서 늘어난 시간1,100 − 310약 790ms
④ 쥐고 놓기 몫310 ÷ 1,100약 28%
⑤ 서로 다투기 몫790 ÷ 1,100약 72%
  • 서로 다투는 비용이 더 컸다 (약 790ms 대 약 310ms)
  • 쥐고 놓기 자체도 싸지 않았다. 다툼 없이도 ++ 한 번당 약 15ns로, 잠그지 않은 ++(약 0.4ns)의 약 39배. 돌리기 전 예측("별로 안 비쌀 것")은 틀렸다
  • "혼자일 때 쥐고 놓기 비용이 둘일 때도 같다"고 가정하고 뺀 대략적인 나누기다. "다툼 쪽이 2배에서 3배쯤 크다" 정도로 기억한다

그럼 lock은 비싸서 못 쓰나 — 아니다

상황잠금 1번(약 15ns)과 비교할 일판단
이번 실험: ++ 하나마다 잠금++ 약 0.4ns잠금이 일보다 39배 큼 → 아깝다
세이브 저장: 저장 1번에 잠금 1번저장 수십 ms저장 시간의 백만 분의 1 수준 → 무시해도 됨

일 하나가 아주 작은데 아주 자주 잠글 때만 비쌉니다. 그래서 순서는 ① 공유 데이터면 일단 막는다(틀린 값은 빨라도 소용없다) ② 느리다는 게 측정으로 확인되면 그때 범위나 도구를 바꾼다.

6 · 잠그는 범위 — for 문 전체를 잠그면 병렬이 사라진다

for 문 전체를 잠그면 값도 맞고 더 빨랐지만, 워커 B는 워커 A가 1,000만 번을 다 끝낼 때까지 아무것도 못 합니다. 스레드 하나가 2,000만 번 더한 것과 같습니다.

코드 모양병렬로 도는 부분
lock 안에 _count++만lock 바깥 (이번 실험에는 바깥 일이 없었다)
lock 안에 for 문 전체없음 (A가 끝나야 B 시작)
for 안에 무거운 계산 + lock 안에 _count++만무거운 계산 부분 ← 병렬이 이득을 보는 모양 (이번에 재지는 않음)

여기서 놓치고 있던 것이 있었습니다. 스레드를 쓰는 목적은 두 가지입니다.

목적뜻for 문 전체를 잠그면
나눠서 빨리워커 여러 개가 일을 나눠 총 시간을 줄인다사라진다
메인 스레드 비워 두기무거운 일을 워커에게 넘겨 게임 화면이 멈추지 않게 한다그대로 남는다

TBH 저장 코드가 두 번째 경우입니다. 세마포어가 저장 전체를 잠가서 저장끼리는 한 번에 하나씩만 돕니다(같은 파일에 동시에 쓰면 깨지니까). 그래도 워커 스레드를 쓴 이유는 JSON 직렬화와 파일 쓰기를 메인 스레드에서 빼내 프레임 드랍을 막으려는 것입니다. 그래서 잠그는 범위를 정하기 전에 먼저 묻습니다. "이 스레드를 나눠서 빨리 하려고 쓰나, 메인 스레드를 비워 두려고 쓰나?"

일은 매번 같은데 2회차만 60배 넘게 느리고, 두 모드의 회차별 모양까지 똑같았습니다. 잠금 방식이 아니라 재는 방법의 문제였습니다.

var stopwatch = System.Diagnostics.Stopwatch.StartNew();
Task workerA = Task.Run(action);
Task workerB = Task.Run(action);
await Task.WhenAll(workerA, workerB);
Debug.Log($"... {stopwatch.ElapsedMilliseconds}ms");   // 이 줄은 언제, 어느 스레드에서 실행되나?

await는 "여기서 기다린다"처럼 보이지만, 실제로는 "이 메서드를 잠깐 빠져나가고, 일이 끝나면 아래 줄부터 마저 실행해 줘"라는 예약입니다. Unity에서는 그 "아래 줄부터"를 메인 스레드가 자기 차례에 실행합니다. await 다음 줄에서도 transform 같은 Unity API를 안전하게 쓰게 하려는 장치입니다 (Unity API는 메인 스레드 전용, Unity 공식 문서).

await를 Task.WaitAll(workerA, workerB)로 바꿔서 다시 재니 5회 모두 7ms에서 8ms로 고르게 나왔습니다. 가설이 값으로 확인됐습니다.

WaitAll은 측정용으로만 썼습니다. 5절의 "한 줄씩 잠금" 두 모드와 1스레드 실험은 await 버전으로 쟀습니다. 5회 모두 값이 고르게 나와 프레임 대기의 영향은 작아 보이지만, WaitAll로 다시 재지는 않았습니다.

8 · lock과 SemaphoreSlim, 무엇을 쓰나

1단계 변수 하나에 연산 하나인가? → Interlocked

2단계 아래 다섯 질문 중 하나라도 "예"인가? → SemaphoreSlim

3단계 다섯 개 다 "아니요"면 → lock. 반납이 자동이라 실수할 여지가 없고, 두 번 반납하는 실수가 생길 수 없고, 이번 측정에서 SemaphoreSlim보다 3배쯤 빨랐습니다. "필요한 이유가 있을 때만 SemaphoreSlim으로 올라간다"를 기준으로 삼았습니다 (커뮤니티 표준).

정리

  1. _count++는 읽기·더하기·쓰기 세 단계라, 두 스레드가 겹치면 더한 값이 덮어써져 사라진다. 에러 없이 가끔만 틀린다
  2. 막는 방법은 세 단계를 한 덩어리로 만드는 것. 변수 하나는 Interlocked, 여러 줄은 lock, await가 끼거나 다른 스레드에서 풀어야 하면 SemaphoreSlim
  3. 잠금은 공짜가 아니다. 다툼 없이도 ++보다 39배, 다투면 140배쯤 비쌌다. 하지만 저장처럼 가끔 한 번 잠그는 곳에서는 무시해도 된다
  4. 잠그는 범위를 넓히면 병렬이 사라진다. 목적이 "메인 스레드 비워 두기"라면 그래도 괜찮다
  5. await 다음 줄은 메인 스레드 차례를 기다린다. Stopwatch로 잴 때 그 대기 시간이 섞일 수 있다

다음 — 데드락

이번 노트는 덜 막아서 생기는 문제였습니다. 다음은 잘못 막아서 생기는 문제, 데드락(deadlock)입니다. 7절에서 본 두 가지 — await 다음 줄은 메인 스레드 차례를 기다린다, 메인 스레드가 그 자리에 멈춰서 기다리면 그 차례가 오지 않는다 — 를 합치면 서로가 서로를 기다리는 상황을 만들 수 있습니다. TBH 저장 코드가 게임 종료 때 세마포어를 워커 스레드에서 반납하는 이유가 바로 이것이라, 다음 노트에서 직접 만들어 보고 설명할 계획입니다.
