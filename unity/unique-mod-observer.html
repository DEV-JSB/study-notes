유니크가 늘 때마다 if가 쌓인다 — Observer 구독으로 옮기기

장비 특수 효과(유니크 모드) 세 개를 일부러 if로 먼저 짜고, Observer 구독으로 리팩토링한 노트. 한 줄 결론: 유니크 코드를 영웅과 전투 흐름에서 빼내고, 영웅은 "지금 피해를 고치는 중이다" 같은 사건만 알린다. 유니크 모드는 필요한 사건만 구독한다. 이때 사건의 순서와 사용 기록을 어디에 둘지가 실제로 설계를 가르는 곳이었다.

발단

회사 프로젝트에는 장비에 붙는 특수 효과(유니크 모드)가 아주 많습니다. 그런데 새 유니크가 하나 생길 때마다 피해 처리 함수나 전투 흐름 함수 안에 if가 하나씩 늘어나는 모양을 자주 봤습니다. 왜 그게 문제인지, 그리고 어떻게 바꾸는지를 직접 해 보고 싶었습니다.

그래서 유니크 세 개짜리 작은 실습을 만들고, 일부러 구조 생각 없이 if로 먼저 짠 다음 리팩토링했습니다. 리팩토링 이유는 처음에 이렇게 정리했습니다.

기존에는 유니크마다 "언제 · 발동해도 되나 · 무엇을 하나"를 매번 새로 구현했다. 이 세 부분(사건 · 조건 · 효과)을 따로 만들어 조립할 수 있게 하면, 새 유니크를 함수 수정 없이 확장할 수 있다.

이 노트는 그 첫 단계입니다. 유니크 하나를 class 하나로 떼어 내고, if 대신 Observer 구독으로 붙입니다. 사건 · 조건 · 효과를 완전히 쪼개는 건 그다음 단계입니다.

유니크규칙
치명상 버티기스테이지당 한 번, 쓰러질 피해를 받으면 체력 1로 버틴다. 같은 스테이지에서 장비를 뺐다 다시 껴도 다시 못 쓴다
다섯 번째 평타 치명타평타 다섯 번째마다 피해 2배
받는 피해 감소받는 피해 10% 감소. 두 개 끼면 20%. 치명상 버티기와 같이 끼면 감소가 먼저고, 쓰러지나 판정은 줄어든 피해로 한다

2. 고치기 전에 동작부터 고정한다

리팩토링은 동작은 그대로 두고 구조만 바꾸는 것입니다. 그래서 먼저 지금 동작을 시나리오 6개로 고정하는 검사기를 만들고, 리팩토링하는 동안 이 파일은 고치지 않았습니다 (특성 테스트, characterization test). 그리고 시나리오 6개가 모두 성공인 지점마다 커밋했습니다. 깨지면 바로 앞 커밋으로 돌아가 그 단계만 다시 하면 됩니다.

시나리오보는 것
유니크 없음기본 피해 처리
치명상 버티기첫 스테이지에서 버팀, 새 스테이지에서 다시 버팀, 같은 스테이지에서는 못 버팀
치명상 버티기 뺐다 끼기같은 스테이지에서 장비를 뺐다 다시 껴도 못 버팀
다섯 번째 평타 치명타평타 10번 중 5번째, 10번째만 치명타
받는 피해 감소한 개 10%, 두 개 20%, 빼면 그만큼 돌아옴
받는 피해 감소 + 치명상 버티기감소 먼저, 판정 나중

검사기를 딱 한 번 고친 적이 있습니다. 실제 게임에서 유니크는 장비에 달려 있고 장비는 고유 번호로 구분됩니다. 같은 유니크가 달린 장비를 두 개 꼈다가 하나를 뺄 때, 유니크 종류만으로는 어느 장비인지 고를 수 없습니다. 그래서 장비 class(Gear, ulong 고유 번호)를 만들고 Equip(gear), Unequip(gearUniqueId)로 바꿨습니다. 이때도 부르는 모양만 바꾸고 정답 값은 한 줄도 안 바꿨고, 6개가 그대로 성공해서 동작이 같다는 걸 값으로 확인했습니다.

3. Observer class를 직접 만든다

회사 선임 코드가 Observer class를 따로 두고 Subscribe / Notify를 쓰는 방식이라, 안이 어떻게 생겼는지 보려고 직접 만들었습니다.

public class Observer<T>
{
    private readonly List<Action<T>> _listeners = new List<Action<T>>();

    public void Subscribe(Action<T> listener)   { _listeners.Add(listener); }
    public void Unsubscribe(Action<T> listener) { _listeners.Remove(listener); }

    public void Notify(T value)
    {
        foreach (var listener in _listeners)
        {
            listener(value);
        }
    }
}
C# event직접 만든 ObserverUniRx Subject
등록 / 해제+= / -=Subscribe / Unsubscribe돌려받은 것을 Dispose()
알리기?.Invoke(...)Notify(...)OnNext(...)
바깥에서 알리기 막기event가 막아 줌안 막힘AsObservable()로 감춤
넘길 값이 없는 사건Action값 없는 class를 따로 만들거나 값을 하나 넘김Subject<Unit>

셋 다 옵저버 패턴이고, 알림 목록을 누가 관리하나가 다릅니다.

치명상 버티기를 위해 처음에는 ShouldSurviveAtOneHp 같은 칸을 상자에 넣으려 했습니다. 그런데 그건 유니크 하나만을 위한 칸이라, 유니크가 늘면 공용 상자에 칸이 계속 늘고 TakeDamage가 그 칸을 읽는 if도 늡니다. if가 쌓이던 문제가 상자로 옮겨 올 뿐이라 넣지 않았습니다. 치명상 버티기는 피해 값을 "체력 − 1"로 고치는 것으로 했습니다.

5. 같은 사건 안에서는 구독 순서가 실행 순서다

처음에는 받는 피해 감소와 치명상 버티기를 둘 다 "피해를 적용하기 직전" 사건 하나에 붙였습니다. 그러자 장비를 낀 순서에 따라 결과가 달라졌습니다. 치명상 버티기 장비를 먼저 끼고 체력 100에 피해 105를 받으면, 치명상 버티기가 줄기 전 피해 105를 보고 "쓰러진다"고 판정해서 쓸 필요가 없는데 써 버립니다. 정답은 105 × 0.9 = 94.5만 받아서 체력 5.5, 치명상 버티기는 안 쓰는 것입니다.

그래서 피해 사건을 두 단계로 쪼갰습니다. 값을 고치는 유니크는 DamageModifying, 판정하는 유니크는 DamageApplying에 붙습니다. 순서는 TakeDamage 안에서 두 사건을 부르는 코드 순서가 정하니, 장비를 어떤 순서로 껴도 "줄이고 나서 판정"이 지켜집니다.

DamageContext damageContext = new DamageContext(incomingDamage);
DamageModifying.Notify(damageContext);                              // 1단계: 값 고치기
damageContext.Damage *= (1f - damageContext.DamageDecreaseRatio);
DamageApplying.Notify(damageContext);                               // 2단계: 판정
// 그다음 체력 깎기

이때 나온 체력 10.900002의 끝자리는 부동소수점 오차입니다 (89.1이 float으로 정확히 표현되지 않음). 소수점 아래 아주 작은 차이는 오차, 딱 떨어지는 차이는 계산식이 다른 것입니다.

6. 유니크 모드 class

public abstract class UniqueModBase
{
    protected Hero _ownerHero;

    public virtual void Attach(Hero hero)
    {
        _ownerHero = hero;
        SubscribeEvents(hero);
    }

    public virtual void Detach()
    {
        UnsubscribeEvents(_ownerHero);
        _ownerHero = null;
    }

    protected abstract void SubscribeEvents(Hero hero);
    protected abstract void UnsubscribeEvents(Hero hero);
}
정한 것이유
abstract class모든 유니크가 "자기 영웅 기억하기, 붙이고 떼기"를 똑같이 한다. 공통 필드와 공통 코드는 부모에 한 번만
숫자는 생성자로EveryNthBaseAttackCriticalMod(5). "세 번째 평타마다 치명타"가 생겨도 class를 새로 안 만들고 (3)으로. 숫자가 들어간 건 게임 아이템 이름(enum 값)이고, class는 동작이다
알림 받는 메서드는 On + 사건 이름OnDamageModifying, OnDamageApplying, OnBaseAttacking. 어느 사건에 붙은 메서드인지 이름으로 보인다
Attach / Detach를 virtual로스테이지 사건이 필요한 유니크(치명상 버티기)만 override해서 구독을 덧붙인다

7. 사용 기록은 어디에 둘까

치명상 버티기의 "이번 스테이지에 썼나"를 어디에 두느냐가 가장 오래 고민한 곳입니다. 기준은 두 질문이었습니다. 언제 지워져야 하나, 무엇을 하면 지워지면 안 되나.

직접 넘겨 보기 — 기록을 둔 곳에 따라

기사와 궁수가 둘 다 치명상 버티기 장비를 끼고 한 스테이지 안에서 아래 일이 차례로 일어납니다. 기록을 어디에 두느냐에 따라 결과가 어떻게 달라지는지 보세요.

세 번째(class의 static Dictionary, 영웅 고유 키 → 횟수)로 했습니다. 영웅마다 겹치지 않는 고유 키(HeroKey)를 붙이고, 스테이지가 시작되면 Dictionary를 통째로 비웁니다. 회사 코드도 "장비를 바꿔도 사라지면 안 되는 값"은 유니크 모드 class의 static에 두고 스테이지 시작 · 재시작 사건에 초기화를 물려 두는 방식이었습니다.

public class SurviveLethalMod : UniqueModBase
{
    // 영웅 고유 키 → 이번 스테이지에 버틴 횟수
    private static Dictionary<int, int> _activateHistory = new();

    public override void Attach(Hero hero)
    {
        base.Attach(hero);
        Stage.OnStageStart.Subscribe(Reset);
    }

    public override void Detach()
    {
        base.Detach();
        Stage.OnStageStart.Unsubscribe(Reset);
    }

    private void Reset(Stage stage)
    {
        _activateHistory.Clear();
    }

    private void OnDamageApplying(DamageContext context)
    {
        if (!_activateHistory.TryGetValue(_ownerHero.HeroKey, out int count) || count <= 0)
        {
            if (_ownerHero.CurrentHp - context.Damage <= 0)
            {
                context.Damage = _ownerHero.CurrentHp - 1f;
                if (!_activateHistory.TryAdd(_ownerHero.HeroKey, 1))
                {
                    _activateHistory[_ownerHero.HeroKey]++;
                }
            }
        }
    }
}

짜면서 실제로 걸린 것

쓴 코드일어난 일바로잡은 것
TryGetValue(...) && count <= 0스테이지 처음엔 기록이 없어서 TryGetValue가 false → 한 번도 안 버팀"기록 없음"은 "아직 안 씀". !TryGetValue(...) || count <= 0
_activateHistory[key]++키가 없을 때 ++의 읽기에서 KeyNotFoundException없으면 넣고, 있으면 더하기 (TryAdd 먼저)
기록 늘리기를 "쓰러질 피해인가" if 바깥에 둠쓰러지지 않는 피해에도 "썼다"로 기록 → 정작 쓰러질 때 못 버팀체력 1로 버티게 한 자리 안에서만 기록
구독과 해제에 람다를 각각 씀글자는 같아도 두 람다는 다른 객체라 해제가 안 되고, 구독이 계속 쌓임구독과 해제에 같은 메서드(Reset)를 넘긴다
장비를 뺄 때 스테이지 사건만 해제장비를 빼도 받는 피해 감소가 계속 20%붙일 때 한 일을 뗄 때 모두 되돌린다 (Detach)

8. 장비 → 유니크 모드 객체는 static 관리자가

Hero가 유니크 모드 객체 목록과 "유니크 종류 → 객체 만들기" switch까지 들고 있으면, 영웅 class에 유니크 사정이 남습니다. 그래서 static UniqueModHandler로 뺐습니다.

누가하는 일
Hero.Equip / Unequip장비 목록에 넣고 빼고, UniqueModHandler에 넘기기만
UniqueModHandler (static)유니크 종류로 객체 만들기, 장비 번호 → 객체 목록, 낄 때 Attach, 뺄 때 Detach

사용 횟수는 static 하나로 두면 영웅끼리 섞였는데, 장비 번호 → 객체 목록은 static 하나로 둬도 됩니다. 장비 고유 번호가 게임 전체에서 겹치지 않아서, 기사의 장비와 궁수의 장비가 같은 칸을 쓸 일이 없기 때문입니다. 같은 static이라도 키가 무엇이냐가 괜찮은지 아닌지를 정했습니다.

새 유니크가 생기면 고칠 곳은 이제 UniqueModHandler의 switch 한 줄과 새 유니크 모드 class 하나입니다. Hero, Battle, Stage에는 유니크 이름이 남지 않습니다.

9. 남겨 둔 것

TakeDamage가 아직 감소 비율을 곱하는 계산까지 하고 있습니다. 이름은 "피해를 받는다"인데 "피해를 어떻게 계산하나"라는 규칙이 섞여 있어서, 다른 종류의 피해 보정이 생기면 이 줄이 다시 늘어납니다. 피해 계산 흐름을 한곳으로 모으는 리팩토링에서 함께 다루기로 하고, 코드에도 그렇게 적어 뒀습니다.

정리

  1. 유니크 코드를 영웅과 전투 흐름에서 빼고, 영웅은 사건만 알린다. 유니크 모드는 필요한 사건만 구독한다
  2. 리팩토링 전에 검사기로 동작을 고정하고, 시나리오가 모두 성공인 지점마다 작게 커밋한다
  3. 사건에 넘기는 값은 구독자가 고칠 수 있는 class 상자. 특정 유니크 전용 칸은 공용 상자에 넣지 않는다
  4. 같은 사건 안에서는 구독 순서가 실행 순서다. 순서가 중요하면 사건을 단계로 쪼개서 코드 순서로 정한다
  5. 숫자는 class 이름이 아니라 생성자 값으로. class는 동작, enum 값은 게임 아이템
  6. 사용 기록은 "언제 지워져야 하나, 무엇을 하면 지워지면 안 되나"로 둘 곳을 정한다. 빼고 끼기로 사라지면 안 되고 영웅끼리 섞이면 안 되면, class의 static Dictionary를 영웅 키로
  7. 구독과 해제에는 같은 메서드를 넘긴다. 람다는 매번 다른 객체다
  8. static으로 모아도 되는지는 키가 겹치느냐로 판단한다

  • 상태 전파 — event, static, ReactiveProperty — event와 UniRx를 처음 비교했던 노트
