박싱 / 언박싱 — Dictionary와 struct

"Dictionary에 struct를 넣으면 박싱, foreach 돌리면 또 박싱 아니냐"는 반문을 Profiler로 직접 재서 확인한 기록. 결론부터: 박싱은 struct를 키로 쓰면서 IEquatable<T>·GetHashCode()를 안 만들었을 때만 생깁니다.

글 버전 boxing-dictionary.md · 실습 원본 unity-study / 01.BoxingUnBoxing

발단

몇백 개짜리 List<T>를 최악 1,000번 돌며 Find를 부르는 코드에 "검색에 유리한 Dictionary로 바꾸자"고 리뷰했더니 이런 반문이 왔습니다.

Dictionary에 struct를 넣으면 박싱이 일어나고, foreach까지 돌리면 또 박싱이 일어나서, GC 때문에 오히려 프레임 드랍이 생기지 않냐

아닐 것 같은데 확신이 없어서 직접 쟀습니다. 확인할 것은 Dictionary × struct × foreach 조합에서 실제로 박싱이 일어나는가.

struct 없음 — int 하나를 object 필드에 넣기

private object _test;

for (int i = 0; i < _iterationCount; ++i)   // _iterationCount = 10000
{
    _test = i;                               // int → object : 박싱 1회
}

프레임당 0 B

키 struct: TestStruct — 아무것도 구현 안 함

public struct TestStruct
{
    public int X;
    public string TestString;
}

private Dictionary<TestStruct, int> _dict = new Dictionary<TestStruct, int>();

for (int i = 0; i < 10; ++i)
{
    foreach (var test in _dict) { }          // Dictionary<K,V>.Enumerator (struct) 그대로 → 힙 안 씀
}

프레임당 0.6 KB · foreach 1번당 ≈60 B

키 struct: TestStruct (구현 없음, 직접 foreach와 같음). 박싱되는 건 키가 아니라 열거자라서 struct 구성은 결과와 상관없음

for (int i = 0; i < 10; ++i)
{
    IEnumerable<KeyValuePair<TestStruct, int>> iterator = _dict;
    foreach (var test in iterator) { }       // GetEnumerator()가 IEnumerator로 반환 → 열거자 박싱 1회
}

요소 1,000개를 돌아도 박싱은 foreach 시작할 때 1번. 요소 수와 무관

프레임당 0.9 KB · 조회 1번당 ≈92 B (32 B × 3)

키 struct: Equals(T) ✗ · GetHashCode() ✗

public struct TestStruct
{
    public int X;
    public string TestString;
    // 아무것도 없음 → 해시는 ValueType.GetHashCode, 비교는 Equals(object)
}

for (int i = 0; i < 10; ++i)
{
    var testStruct = new TestStruct();
    testStruct.X = i;
    _dict.TryGetValue(testStruct, out int value);   // 해시 1회 + 비교 2회 = 박싱 3회
}

프레임당 0.3 KB · 조회 1번당 ≈32 B (박싱 1회)

키 struct: Equals(T) ✓ · GetHashCode() ✗

public struct TestStruct2 : IEquatable<TestStruct2>
{
    public int X;
    public string TestString;
    public bool Equals(TestStruct2 other) => other.X == X;   // 비교 경로 → 0회
    // GetHashCode() 없음 → 해시는 여전히 ValueType.GetHashCode
}

private Dictionary<TestStruct2, int> _dict2 = new Dictionary<TestStruct2, int>();

for (int i = 0; i < 10; ++i)
{
    var testStruct = new TestStruct2();
    testStruct.X = i;
    _dict2.TryGetValue(testStruct, out int value);  // 해시 1회만 남음 = 박싱 1회
}

측정 예정 · 예상 0 B

키 struct: Equals(T) ✓ · GetHashCode() ✓ — 앞 케이스의 TestStruct2에 한 줄을 추가한 것. 저장소의 지금 코드가 이 상태

public struct TestStruct2 : IEquatable<TestStruct2>
{
    public int X;
    public string TestString;
    public bool Equals(TestStruct2 other) => other.X == X;   // 비교 경로 → 0회
    public override int GetHashCode() => X;                  // 해시 경로 → 0회 (Equals와 같은 필드 X)
}

// 조회 코드는 앞 케이스와 같음
_dict2.TryGetValue(testStruct, out int value);

2 · 박싱 1회는 몇 바이트인가

박싱 1번 할 때마다 힙에 20 B짜리 상자가 새로 하나 생깁니다. "5배"도 이 한 번에 대한 말이에요.

측정에서 1회 값을 꺼내는 순서계산값
① Profiler가 보여 준 값 (object o = i;를 10,000번)—195.3 KB
② 바이트로 (Profiler의 KB는 1,024 B)195.3 × 1,024≈ 200,000 B
③ 1번으로 나누기200,000 ÷ 10,00020 B
20 B가 어디서 나왔나 (64비트 기준)크기
값 자체 (int)4 B
객체 헤더 — 타입 포인터 (이 상자가 int라는 표시)8 B
객체 헤더 — 동기화 블록 (lock 등에 쓰는 칸)8 B
합계 = 박싱 1번에 새로 생기는 상자20 B
  • 값은 4 B인데 담는 상자가 20 B → 박싱 1번마다 4 B짜리 값 하나가 20 B를 쓰게 됩니다 (5배). 10,000번이면 상자가 10,000개라서 200,000 B
  • 원래의 int(스택 4 B)는 그대로 있고, 힙에 복사본 상자가 추가로 생기는 것. 이 상자가 GC가 치워야 할 쓰레기가 됩니다

그림으로 — int 박싱과 실험 struct 박싱

  • 헤더 16은 int 줄의 헤더와 똑같은 것입니다. 타입 포인터 8 + 동기화 블록 8. 무엇을 박싱하든(심지어 class를 new 해도) 힙 객체에는 이 16 B가 붙어요. 그래서 박싱 비용 = 값 크기 + 16
  • 패딩 4: 다음 칸인 참조(8 B)를 8의 배수 위치에 놓으려고 비워 두는 자리 (공식 문서: 필드 정렬)
  • string 참조 8: 글자들이 아니라 "글자가 있는 곳의 주소"만 복사됩니다. 그래서 문자열 길이와 상관없이 8 B

직접 측정 + 계산 · 헤더·참조 크기는 64비트 런타임 기준

3 · 자리마다 위험이 다르다

자리박싱?이유
값(Value)거의 안 함담기는 대상이라 해시·비교가 필요 없음. 예외: ContainsValue()는 처음부터 훑으며 비교
foreach안 함열거자도 struct, KeyValuePair도 struct
foreach를 인터페이스로 받아서1회struct 열거자가 인터페이스로 박싱. foreach 1번당 1개라 요소 수와 무관 — "그냥 돌렸는데 박싱"이 사실이 되는 유일한 경우
키(Key)3회아래 두 경로

키 자리의 위험은 GC(박싱), 값 자리의 위험은 복사 비용. 성격이 다른 문제입니다.

4 · 키 조회의 두 경로 — 켜 보기

struct에 무엇을 구현하느냐에 따라 박싱이 어느 경로에서 사라지는지 봅니다. 두 경로는 완전히 별개라 하나만 하면 하나만 사라집니다.

조회 1회 박싱 3회 예상 할당 96 B 
public struct SlotKey : IEquatable<SlotKey>
{
    public int X;
    public bool Equals(SlotKey other) => other.X == X;   // ② 비교 경로
    public override int GetHashCode() => X;              // ① 해시 경로 — Equals와 같은 필드 X
}
  • Add, Remove, ContainsKey, 인덱서 — 키를 다루는 모든 연산이 같은 경로라, 한 번 잘못 쓰면 아주 자주 터집니다
  • Equals와 GetHashCode는 같은 필드 기준으로. "같으면 해시도 같다"가 깨지면 넣었는데 못 찾습니다 (공식 문서)

경로 설명: EqualityComparer<T>.Default가 타입에 따라 비교기를 고름 (공식 문서) · 바이트는 측정값 기준 추정 (92 B ≈ 96 B)

5 · 박싱은 언제 일어나나

한 문장: 값 타입이 참조 타입으로 취급되는 순간. 그 순간이 네 군데입니다.

#언제예이 실습에서
1object로 넘어갈 때object o = i;
string.Format("{0}", i)		Equals(object)
2인터페이스로 취급될 때IEnumerable<…> it = dict;인터페이스 foreach
3struct가 override 안 한 상속 메서드를 부를 때myStruct.GetHashCode()
myStruct.ToString()		ValueType.GetHashCode()
4params object[]인자마다 박싱 + 배열 할당—
  • 3번은 매개변수가 없어도 일어납니다 → "매개변수가 object인지 보면 된다"로는 못 잡음
  • 3번은 struct만. 클래스는 처음부터 힙에 있어서 옮길 게 없습니다

반대로 안전한 것

void Foo<T>(T value);       // int를 넘겨도 박싱 없음 — 런타임이 값 타입 전용 코드를 만듦
List<int>.Add(int item);    // 박싱 없음
StringBuilder.Append(int);  // 값 타입 전용 오버로드

확인하는 법

  • 시그니처를 본다 — 인자 자리가 object·인터페이스면 박싱, T·구체 값 타입이면 안전
  • 오버로드가 여러 개라 컴파일러 선택을 모르면 → IL을 보거나, 박싱이 불가능한 형태로 바꿔서 같은 숫자가 나오는지 잰다 (2편에서 실제로 씀)

결론

  • 반문은 틀렸다. Dictionary에 struct를 넣는 것도, foreach도 박싱을 만들지 않는다
  • 문제는 struct 키 + 구현 누락뿐이고, 두 줄이면 0
  • 제안한 리팩터링은 그대로 진행됐고, 리뷰어도 스스로 정정해 Dictionary로 바꿨다
  • 내 기준: struct를 키로 쓰면 IEquatable<T> + GetHashCode()를 반드시 같이 (취향 · 바꿔도 됨)
