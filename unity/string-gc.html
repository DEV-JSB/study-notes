문자열과 GC

+, $"", string.Format, StringBuilder — 무엇이 박싱하고 무엇이 GC를 얼마나 만드나 직접 잰 기록. 한 줄 결론: 만드는 방법을 바꾸면 최대 15% 차이, 값이 바뀔 때만 만들면 66배 차이.

글 버전 string-gc.md · 실습 원본 unity-study / 02.StringGC · 이어지는 편 1편 박싱

발단

1편에서 박싱을 쟀지만 와닿지 않았습니다. IEquatable 없는 struct 키는 실무에서 거의 안 나오니까요. 그래서 게임 개발에서 매일 쓰는 문자열로 옮겼습니다. 문자열이 박싱·GC와 관계있다는 건 얕게 알았지만, 정확히 어떤 방식이 무엇을 만드는지는 몰랐습니다.

2 · 문자열 하나는 몇 바이트 — 직접 넣어 보기

공식: 22 + 글자수 × 2. 헤더 16, 길이 필드 4, 널 종료 2, 글자마다 2 (UTF-16).

계산 · 예: "Score : 5999"는 12글자 → 22 + 12 × 2 = 46 B

3 · 한 줄 실행하면 힙에 무엇이 생기나

Profiler가 잡는 건 그 줄을 실행하는 동안 힙에 새로 생긴 것 전부입니다. 결과 문자열 하나만 생기는 게 아니라, 만드는 도중에 잠깐 쓰고 버리는 것도 같이 잡혀요. 그래서 개당 측정값(65.6 B, 75.3 B)이 결과 문자열 크기보다 큽니다.

i = 5999일 때 한 번 실행하면:

  • ②는 두 방식이 똑같습니다. 다른 건 ①, 숫자를 넘기는 방식뿐이에요
    • 2·3번은 숫자를 상자에 담아 넘긴다 → 상자 20 B (1편에서 잰 바로 그 값)
    • 1·4번은 숫자를 문자열로 바꿔서 넘긴다 → "5999" = 22 + 4 × 2 = 30 B

측정값과 맞춰 보기 (평균)

실험은 i를 0~5999까지 돌렸으니 글자 수가 매번 다릅니다. 평균을 내면:

평균 글자 수크기

숫자 문자열 (1·4번의 ①)3.8자리22 + 7.6 = 29.6 B

5번: 값이 0~99라 결과 평균 9.9자 → 67.6 B × 100개 = 6,760 B = 6.6 KB. 글자가 짧아진 만큼 개당 크기도 작아서 감소폭이 정확히 60배가 아니라 66.8배

4 · 알아낸 것

박싱을 안 하는 방식이 메모리를 더 썼다

비교한 네 줄 (실험 코드 그대로, 전체 코드: StringGC.cs):

// 박싱하는 방식 — 숫자 i가 object 인자로 넘어감
_str = $"Score : {i}";                                       // 2번
_str = string.Format("Score : {0}", i);                      // 3번

// 박싱 안 하는 방식 — 숫자 i를 먼저 문자열로 바꿔서 붙임
_str = "Score : " + i;                                       // 1번
_builder.Clear();
_str = _builder.Append("Score : ").Append(i).ToString();     // 4번
박싱하는 방식 (2·3번)박싱 안 하는 방식 (1·4번)
숫자를 어떻게 넣나숫자를 상자에 담아 넘기고, 결과 문자열에 자릿수를 바로 써넣음숫자를 먼저 "5999" 같은 문자열로 바꾼 뒤 붙임
결과 문자열 말고 더 생기는 것박싱 상자 20 B숫자 문자열 약 30 B
문자열 1개 만들 때 쓴 메모리65.6 B75.3 B (15% 더 큼)

"박싱을 피했다" ≠ "메모리를 덜 쓴다". 1편만 하고 나면 박싱만 없애면 된다고 생각하기 쉬운데, 박싱은 여러 비용 중 하나일 뿐입니다. 박싱을 없애는 대신 다른 것(숫자 문자열)을 만들면 오히려 더 쓸 수 있어요.

$""는 컴파일되면 string.Format과 똑같아진다

2번($"Score : {i}")과 3번(string.Format("Score : {0}", i))이 384.6 KB로 소수점까지 똑같았습니다. "비슷하다"면 아무것도 알 수 없지만, "정확히 같다"는 두 줄이 같은 코드로 컴파일됐다는 뜻이에요. 측정으로 컴파일러 동작을 알아낸 셈입니다.

$"Score : {i}"   → 컴파일러가 바꿔 넣음 →   string.Format("Score : {0}", i)

주의 (공식 문서): Unity가 쓰는 C# 9 기준. C# 10 + .NET 6 이상에서는 $""가 DefaultInterpolatedStringHandler로 바뀌어 박싱 없이 만들어집니다. Unity가 그 버전으로 올라가면 다시 재 볼 것.

StringBuilder는 "조각 2개를 한 번 붙이고 끝"일 때는 이점이 없다

이 실험의 4번 코드는 이렇습니다. "Score : "와 숫자, 조각 2개를 한 번 붙이고 바로 결과를 꺼냅니다.

_builder.Clear();
_str = _builder.Append("Score : ").Append(i).ToString();

결과는 1번("Score : " + i)과 똑같이 441.0 KB. 아낀 게 하나도 없습니다. 이유는 둘:

  1. StringBuilder가 아껴 주는 건 "이어 붙이는 도중에 생기는 문자열"이에요. 그런데 조각이 2개면 +도 도중에 생기는 문자열이 없습니다 (컴파일러가 string.Concat 한 번으로 바꿔 줌). 아낄 게 처음부터 없었어요
  2. 마지막 ToString()이 결과 문자열을 어차피 만듭니다. StringBuilder 안의 버퍼는 char[]라서, string이 필요하면 새로 만들어야 해요

StringBuilder가 이기는 건 루프를 돌면서 계속 이어 붙일 때입니다 (이번엔 측정 안 함 · 커뮤니티 표준).

// + 로 누적: 돌 때마다 점점 긴 새 문자열이 생긴다
string s = "";
for (int k = 0; k < 5; ++k) s += k;     // "0", "01", "012", "0123", "01234" → 5개 생김

// StringBuilder로 누적: 버퍼 하나에 계속 써넣고 마지막에 1개만
var sb = new StringBuilder();
for (int k = 0; k < 5; ++k) sb.Append(k);
string s2 = sb.ToString();              // "01234" → 1개
이렇게 붙일 때고를 것
한 줄에서 조각 2~3개 ("HP: " + hp)+ 또는 $"" — 어차피 Concat 한 번
루프를 돌며 계속 이어 붙임 (로그 여러 줄, 목록 출력)StringBuilder

기준은 "얼마나 자주 만드나"가 아니라 "한 문자열을 만들 때 몇 번에 걸쳐 붙이나".

+가 박싱 안 하는 걸 어떻게 확인했나

  • string.Format(string, object)는 시그니처만 봐도 박싱 확정 (인자가 object)
  • +는 연산자라 소스에 메서드 이름이 없다 → 컴파일러가 string.Concat 오버로드 중 뭘 골랐는지 코드에서 안 보임
  • 그래서 박싱이 절대 일어날 수 없는 형태로 바꿔서 쟀다
_str = "Score : " + i.ToString();   // 직접 문자열로 바꿔서 넘김 → 박싱 불가능
// 결과 441.0 KB = 1번과 같음 → 1번도 원래 ToString()으로 바꾼 뒤 문자열끼리 붙이고 있었다

시그니처로 판단이 안 되면, 의심 요소를 없앤 버전을 만들어 숫자가 같은지 본다.

어떤 방법으로 만드느냐보다, 안 만들어도 되는 프레임에 안 만드는 게 훨씬 크다

1~4번과 5번의 차이는 "만드는 방법"이 아니라 "몇 번 만드느냐"입니다.

한 프레임에 도는 횟수그중 문자열을 만드는 횟수프레임당 메모리
1~4번 (방법만 다름)6,000번6,000번 (매번)384.6 ~ 441.0 KB
5번6,000번100번 (값이 바뀔 때만)6.6 KB
  • 1~4번끼리는 방법을 아무리 바꿔도 차이가 최대 15%
  • 5번은 만드는 방법은 1번과 같은 +인데, 만드는 횟수를 줄여서 66배 줄었다

5번 코드 — 직전에 만든 값을 기억해 두고, 값이 그대로면 건너뜁니다.

int value = i / 60;              // 60번 돌 때마다 1씩 바뀌는 값 (0~99)
if (value != _lastValue)         // 직전과 같으면 문자열을 만들지 않음
{
    _str = "Score : " + value;
    _lastValue = value;
}

실전에서는 UI가 이 모양입니다. 체력 표시를 Update()에서 매 프레임 hpText.text = "HP: " + hp;로 갱신하면, 체력이 그대로여도 매 프레임 새 문자열이 생겨요. 화면 글자는 똑같은데 GC 쓰레기만 쌓입니다. 체력이 바뀐 프레임에만 갱신하면 됩니다.

결론 — 판단 순서

박싱은 방법에 따라 생기기도 안 생기기도 하지만, 문자열을 하나 만들면 그 문자열만큼의 힙 할당은 반드시 생깁니다. 결과 문자열 45.6 B는 어떤 방법이든 남아요. 그래서 방법을 바꿔서 줄일 수 있는 건 최대 15%.

  1. 값이 바뀐 프레임에만 문자열을 만든다 — 이번 실험에서 66배. 대부분 여기서 끝
  2. 만들어야 하면 읽기 좋은 방법을 쓴다 — 방법끼리 차이는 최대 15%라 가독성을 버릴 이유가 없다. $""가 제일 읽기 쉽고 측정상 제일 작기도 했다 (취향 · 바꿔도 됨)
  3. 루프를 돌며 이어 붙일 때만 StringBuilder

재지 않았지만 알아둘 것

이번 측정표와 구분합니다

  • TextMeshPro SetText("HP: {0}", currentHp) — 포맷은 리터럴, 숫자는 TMP 내부 char[]에 직접 씀, 인자는 float이라 박싱 없음 → 문자열 객체 0개 (공식 문서)
  • SetText(StringBuilder) — ToString() 없이 문자를 직접 읽어 감 → 4번에서 마지막 ToString()이 만들던 결과 문자열까지 안 생김
  • Debug.Log — 위 비용 + 파일 I/O + 스택 트레이스 문자열(이게 제일 큼). 빌드에도 남으니 매 프레임 코드엔 넣지 말고 조건부 컴파일([Conditional])도 고려 (커뮤니티 표준)

더 보기
