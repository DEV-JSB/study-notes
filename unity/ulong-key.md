## 발단

회사 프로젝트에서 enum 두 개의 조합으로 `Dictionary` 키를 만들어야 했던 적이 있다. 튜플을 쓰기 싫어서 AI에게 물어 `ulong` 하나에 두 값을 담는 `MakeKey`를 썼는데, 그때는 **왜 그 모양인지 모른 채** 가져다 썼다. 기억에 남은 건 "ulong을 나눠서 플래그처럼 세운다"는 흐릿한 말뿐이었다.

그 흐릿한 말을 비트 그림으로 바꿔 보니 두 갈래로 나뉘었다. 그래서 둘 다 직접 만들어 보고 비교했다.

- **A. 숫자 그대로 넣기 (bit packing)**: 칸 묶음 하나에 enum 번호를 2진수 그대로 넣는다
- **B. 비트 하나씩 켜기 (bit flag)**: 칸 묶음 안에서 enum 번호번 칸 하나만 켠다

**한 줄 결론: 둘 다 키는 만들어진다. 하지만 enum 하나에 값이 한 번에 하나뿐이면 A가 맞는 도구다. B는 "여러 개를 동시에 켜고 끄기"를 위한 형식이라, 키로 쓰면 장점은 못 쓰고 32개 제한과 칸 찾기라는 단점만 떠안는다.**

실습에 쓴 enum은 이 두 개다.

```csharp
public enum ItemType { Weapon, Armor, Potion, Ring }  // 0, 1, 2, 3
public enum Grade    { Normal, Rare, Epic, Legend }   // 0, 1, 2, 3
```

## 1. 64칸을 왼쪽 32칸과 오른쪽 32칸으로 나눈다

`ulong`은 64비트다. 2진수로 가로로 적으면 **맨 왼쪽이 63번 비트, 맨 오른쪽이 0번 비트**다. 이걸 가운데에서 잘라 반씩 쓴다.

| | 왼쪽 32칸 (63 ~ 32번 비트) | 오른쪽 32칸 (31 ~ 0번 비트) |
|---|---|---|
| 담는 것 | Grade | ItemType |
| 다른 문서에서 부르는 이름 | 상위 32비트 (high bits) | 하위 32비트 (low bits) |

64칸은 머릿속에 잘 안 들어온다. 이 노트의 그림은 **8칸으로 줄여서** 그린다. 왼쪽 4칸이 Grade, 오른쪽 4칸이 ItemType이다. ulong에서는 4를 32로 바꾸기만 하면 된다.

## 2. enum은 이름이 붙은 int다

C# enum은 따로 정하지 않으면 안쪽 자료형(underlying type)이 `int`다 (공식 문서). `ItemType.Armor`는 메모리 안에서 그냥 int 1이고, 컴퓨터는 모든 정수를 2진수 비트로 저장한다.

| 이름 | int 값 | 비트 (오른쪽 4칸) |
|---|---|---|
| Weapon | 0 | `0000` |
| Armor | 1 | `0001` |
| Potion | 2 | `0010` |
| Ring | 3 | `0011` |

Ring(3)은 비트가 **두 개** 켜져 있다. 일반 enum은 "비트 하나 = 값 하나"가 아니다. 이 차이가 A와 B를 가른다.

| | 값 | 켜진 비트 수 |
|---|---|---|
| 일반 enum (ItemType) | 0, 1, 2, 3 | 값마다 다름 (3은 두 개) |
| 플래그 enum (앞 노트의 `[Flags]`) | 1, 2, 4, 8 | 항상 하나 |

## 3. A 숫자 그대로 넣기

### 10진수로 먼저

아이템 번호 3과 등급 번호 2를 숫자 하나로 묶으려면 이렇게 하면 된다.

| 단계 | 계산 | 결과 |
|---|---|---|
| 아이템 번호를 앞자리로 보내기 | 3 × 100 | 300 |
| 등급 번호를 뒷자리에 놓기 | + 2 | 302 |

"앞 두 자리는 아이템, 뒤 두 자리는 등급"이라고 약속하면 302만 보고도 둘을 다시 알아낼 수 있다. A는 이 일을 2진수로 하는 것이다.

### 2진수로 (8칸 예시: Epic(2) + Armor(1))

| | 왼쪽 4칸 (Grade) | 오른쪽 4칸 (ItemType) | 값 |
|---|---|---|---|
| 키 | `0010` | `0001` | 2 × 16 + 1 = 33 |

| | 10진수 | 8칸 2진수 | ulong |
|---|---|---|---|
| 앞쪽으로 보내기 | × 100 | × 16 = `<< 4` | × 2³² = `<< 32` |

```csharp
public static ulong MakePackedKey(ItemType itemType, Grade grade)
{
    ulong key = 0;

    key |= (ulong)itemType;           // 밀지 않음 → 오른쪽 32칸
    key |= ((ulong)grade << 32);      // 32칸 밀기 → 왼쪽 32칸

    return key;
}
```

ulong에서 Epic(2) + Armor(1)의 키는 2 × 2³² + 1 = **8589934593**이다.

`(ulong)grade << 32`는 **먼저 ulong으로 바꾸고 나서** 민다. 순서를 바꿔 `(ulong)((int)grade << 32)`로 쓰면 int 안에서 32칸을 밀게 되는데, int 시프트는 횟수를 32로 나눈 나머지만 쓰므로 0칸을 민다 (공식 문서, 앞 노트 8절).

## 4. A에서 꺼내기 — 몫과 나머지

만들 때 "× 2³² 하고 더했다"면, 꺼낼 때는 2³²으로 나눠서 **몫과 나머지**를 따로 가져간다.

| | 10진수 | 8칸 2진수 | ulong |
|---|---|---|---|
| 만들기 | 3 × 100 + 2 = 302 | 2 × 16 + 1 = 33 | |
| 왼쪽 값 (몫) | 302 ÷ 100의 몫 = 3 | 33 ÷ 16의 몫 = 2 | `key >> 32` |
| 오른쪽 값 (나머지) | 302 ÷ 100의 나머지 = 2 | 33 ÷ 16의 나머지 = 1 | 왼쪽 32칸 지우기 |

### 왼쪽(Grade) 꺼내기: `>>`로 끌어내린다

`>>`는 모든 칸을 오른쪽으로 옮긴다. 규칙은 두 개다.

- 오른쪽 끝을 넘어간 칸은 **버려진다**
- 왼쪽에 새로 생긴 빈칸은 **0으로 채워진다** (ulong 기준)

| 밀기 | 왼쪽 4칸 | 오른쪽 4칸 | 값 | 일어난 일 |
|---|---|---|---|---|
| 키 그대로 | `0010` | `0001` | 33 | |
| `>> 1` | `0001` | `0000` | 16 | 0번의 1(Armor)이 오른쪽 끝으로 떨어져 사라짐 |
| `>> 2` | `0000` | `1000` | 8 | Epic의 1이 경계를 넘어옴 |
| `>> 3` | `0000` | `0100` | 4 | |
| `>> 4` | `0000` | `0010` | 2 | 왼쪽 4칸의 `0010`이 통째로 오른쪽 4칸에 도착 → Epic |

```csharp
public static Grade GetGradeFromPackedKey(ulong packedKey)
{
    ulong key = packedKey >> 32;
    int value = (int)key;
    return (Grade)value;
}
```

### 오른쪽(ItemType) 꺼내기: 옮기지 않고 왼쪽만 지운다

ItemType은 이미 0번 칸부터, 즉 원래 있어야 할 자리에 있다. 문제는 왼쪽에 붙은 Grade 하나다.

| | 왼쪽 4칸 | 오른쪽 4칸 | 값 |
|---|---|---|---|
| 키 | `0010` | `0001` | 33 |
| 원하는 것 (Armor) | `0000` | `0001` | 1 |

지우는 방법을 세 가지 다 만들어 봤다. 결과는 모두 같다.

| 방법 | 코드 | 원리 |
|---|---|---|
| 1. 마스크로 지우기 | `key & ((1UL << 32) - 1)` | 마스크의 왼쪽은 전부 0, 오른쪽은 전부 1. AND는 둘 다 1인 칸만 남긴다 |
| 2. 밀어서 떨어뜨렸다가 되돌리기 | `(key << 32) >> 32` | `<< 32`에서 Grade가 **왼쪽 끝 밖으로** 떨어지고, `>> 32`로 ItemType이 제자리로 온다 |
| 3. 작은 상자에 담기 | `(int)key` | 64칸을 32칸 상자로 캐스트하면 안 들어가는 왼쪽 32칸이 잘린다 (공식 문서: 명시적 정수 변환은 높은 쪽 비트를 버림) |

방법 2를 8칸으로 보면 이렇다.

| 단계 | 왼쪽 4칸 | 오른쪽 4칸 | 일어난 일 |
|---|---|---|---|
| 키 | `0010` | `0001` | |
| `<< 4` | `0001` | `0000` | Grade(`0010`)가 왼쪽 끝으로 떨어져 사라지고 ItemType이 왼쪽으로 감 |
| `>> 4` | `0000` | `0001` | ItemType만 제자리로 → Armor |

세 방법 모두 **"ulong 상자는 64칸으로 정해져 있어서, 밖으로 밀려난 비트는 버려진다"**는 같은 원리를 쓴다. 실무 코드에서는 의도가 바로 읽히는 방법 1(마스크)이나 3(캐스트)을 더 자주 본다 (커뮤니티 표준). 방법 2는 `long`처럼 부호 있는 자료형에서는 `>>`가 빈칸을 부호 비트로 채워서 (공식 문서: 산술 시프트) 음수가 나올 수 있다.

```csharp
public static ItemType GetItemTypeFromPackedKey(ulong packedKey)
{
    ulong key = packedKey & ((1UL << 32) - 1);   // 방법 1
    int value = (int)key;
    return (ItemType)value;
}
```

### 마스크 `(1UL << 32) - 1`을 만드는 세 가지 방법

오른쪽 32칸만 1인 수가 필요하다. 1이 n개인 2진수 = 2ⁿ − 1이라는 건 앞 노트 7절에서 정리했다.

| 방법 | 코드 | 설명 |
|---|---|---|
| 계산 | `(1UL << 32) - 1` | 1 뒤에 0이 32개인 수에서 1을 뺀다. 10진수 1000 − 1 = 999와 같은 원리 |
| 16진수 | `0xFFFFFFFFUL` | 16진수 F 한 글자 = 2진수 `1111` 네 칸. 32칸 ÷ 4 = F 8개 (커뮤니티 표준) |
| 이미 있는 값 | `(ulong)uint.MaxValue` | uint는 32칸이라 가장 큰 값이 32칸 전부 1 |

세 값은 모두 4294967295다.

### 왜 Grade에는 세 방법이 안 통하나

ItemType에 쓴 세 방법을 Grade(왼쪽)에 그대로 써 보면 모두 틀린다.

| 방법 | 왼쪽 4칸 | 오른쪽 4칸 | 값 | 판정 |
|---|---|---|---|---|
| 1. 마스크 `& 1111_0000` | `0010` | `0000` | 32 | 2가 아님 |
| 2. `>> 4` 다음 `<< 4` | `0010` | `0000` | 32 | 2가 아님 |
| 3. 4칸 상자로 캐스트 | (잘림) | `0001` | 1 | 반대쪽(Armor)이 남음 |
| `>> 4` 한 번 | `0000` | `0010` | 2 | Epic |

**숫자의 값은 0번 칸부터 읽는다.** ItemType은 이미 0번 칸부터 있어서 지우기만 하면 되지만, Grade는 4번 칸(ulong에서는 32번 칸)부터 있어서 지워도 2 × 16 = 32로 읽힌다. 그래서 Grade는 반드시 **옮겨야** 하고, `>>`로 옮기면 오른쪽 칸은 덤으로 떨어져 나간다. 지우기가 옮기기 안에 이미 들어 있다.

| 꺼낼 것 | 해야 할 일 | 방법 |
|---|---|---|
| Grade (왼쪽) | 오른쪽을 버리고, 왼쪽을 오른쪽으로 옮기기 | `>> 32` 한 번 = 몫 |
| ItemType (오른쪽) | 왼쪽만 버리기 (옮길 필요 없음) | 마스크 / `<<` 다음 `>>` / 캐스트 = 나머지 |

## 5. B 비트 하나씩 켜기

B는 앞 노트의 비트 플래그처럼 `1 << 번호`로 칸 하나를 켠다. ItemType은 오른쪽 32칸의 itemType번 칸, Grade는 왼쪽 32칸의 grade번 칸이다.

| 8칸 예시: Epic(2) + Armor(1) | 왼쪽 4칸 (Grade) | 오른쪽 4칸 (ItemType) |
|---|---|---|
| A. 숫자 그대로 | `0010` (숫자 2) | `0001` (숫자 1) |
| B. 비트 하나씩 | `0100` (2번 칸) | `0010` (1번 칸) |

```csharp
public static ulong MakeFlagKey(ItemType itemType, Grade grade)
{
    ulong itemFlag = 1UL << (int)itemType;                // 오른쪽 32칸의 itemType번 칸
    ulong gradeFlag = (1UL << 32) << (int)grade;          // 왼쪽 32칸의 grade번 칸 = 32 + grade번 칸

    return itemFlag | gradeFlag;
}
```

## 6. B에서 꺼내기 — 같은 ulong이라도 형식이 다르다

처음에는 "B에서 ItemType 꺼내기도 A와 똑같이 왼쪽 32칸만 지우면 되지 않나?"라고 생각했다. 왼쪽 32칸을 지운 뒤 남는 오른쪽 32칸을 비교해 보면 다르다.

| ItemType | A의 오른쪽 32칸 | 값 | B의 오른쪽 32칸 | 값 |
|---|---|---|---|---|
| Weapon (0) | `0000` | 0 | `0001` | 1 |
| Armor (1) | `0001` | 1 | `0010` | 2 |
| Potion (2) | `0010` | 2 | `0100` | 4 |
| Ring (3) | `0011` | 3 | `1000` | 8 |

A는 남은 값이 곧 enum 번호다. B는 남은 값이 `1 << 번호`의 **결과**라서, Potion을 꺼내면 2가 아니라 4가 나온다. B에는 "**몇 번 칸이 켜져 있나**"를 찾는 단계가 하나 더 있다.

| 단계 | A | B |
|---|---|---|
| 1. 필요 없는 절반 지우기 | 같음 | 같음 |
| 2. 번호로 바꾸기 | 필요 없음 | 켜진 칸 번호 찾기 (4 → 2, 8 → 3) |
| 3. enum으로 바꾸기 | 같음 | 같음 |

자료형은 둘 다 ulong이지만 **안에 담긴 약속(형식, encoding)이 다르다.** ulong만 봐서는 어느 약속으로 만든 키인지 알 수 없으므로, 만드는 메서드와 꺼내는 메서드는 항상 짝이 맞아야 한다. A로 만든 키를 B 방식으로 꺼내면 컴파일은 되지만 값이 틀린다.

켜진 칸은 0번 칸부터 하나씩 확인해서 찾았다. 앞 노트의 `IsOn`을 32번 반복하는 것과 같다.

```csharp
public static ItemType GetItemTypeFromFlagKey(ulong flagKey)
{
    for (int i = 0; i < 32; ++i)
    {
        ulong flag = 1UL << i;

        if ((flagKey & flag) != 0)
        {
            return (ItemType)i;
        }
    }
    return default;
}

public static Grade GetGradeFromFlagKey(ulong flagKey)
{
    ulong key = flagKey >> 32;          // A에서 쓴 >> 32로 먼저 왼쪽 32칸을 오른쪽으로 옮긴다
    for (int i = 0; i < 32; ++i)
    {
        ulong flag = 1UL << i;

        if ((key & flag) != 0)
        {
            return (Grade)i;
        }
    }
    return default;
}
```

`GetGradeFromFlagKey`는 A에서 쓴 `>> 32`를 먼저 해서, ItemType과 같은 루프를 다시 쓸 수 있게 만들었다.

### 더 다듬을 수 있는 곳

동작은 맞지만 이 코드에는 다듬을 곳이 남아 있다.

| 볼 곳 | 지금 | 다듬는다면 |
|---|---|---|
| 같은 루프가 두 번 | 메서드마다 복사 | "켜진 칸 번호 찾기(ulong)" 도우미 메서드 하나로 빼고, 두 메서드는 넘길 절반만 다르게 |
| `GetItemTypeFromFlagKey`가 왼쪽 32칸을 안 지움 | 루프가 0~31번만 봐서 우연히 맞음 | 마스크로 먼저 지워서 의도를 드러내기 |
| 켜진 칸이 없으면 `default` | 잘못된 키도 조용히 Weapon이 됨 | 예외를 던져서 버그를 숨기지 않기 |

"오른쪽 끝부터 0이 몇 개 이어지나"를 바로 세는 연산(trailing zero count)도 있어서 루프 대신 쓸 수 있다. 지금은 넘어간다.

## 7. 실제로 걸린 함정

이번 실습에서 직접 걸린 것들이다. 1번과 5번은 앞 노트에서 정리했던 내용인데 또 걸렸다. 읽고 이해한 것과 직접 쓸 때 손이 그렇게 움직이는 것은 다르다는 걸 다시 확인했다.

| 번호 | 쓴 코드 | 무슨 일이 일어났나 | 피하는 법 | 컴파일러가 잡나 |
|---|---|---|---|---|
| 1 | `ulong flag = 1 << 32;` | 그냥 쓴 `1`은 int라서 횟수를 32로 나눈 나머지(0칸)만 밀고 1이 됨 | ulong 키면 `1UL`부터 | 못 잡음 |
| 2 | `1L << 32L` | 시프트 칸 수는 int여야 함 | 칸 수는 항상 int | 잡음 |
| 3 | `int itemFlag` \| `ulong gradeFlag` | 부호 있는 int와 부호 없는 ulong을 섞어 연산할 수 없음 | 처음부터 전부 ulong | 잡음 |
| 4 | `key &= (1UL << 32 - 1);` | `-`가 `<<`보다 먼저 계산돼서 `1UL << 31`이 됨. 마스크가 31번 칸 하나뿐이라 ItemType이 전부 0 | 비트 연산은 괄호로 순서를 정하기 | 못 잡음 |
| 5 | `(flagKey & flag) == 1` | AND 결과는 1이 아니라 그 칸의 자리값(2, 4, 8…)이라 0번 칸에서만 참 | `!= 0`, 또는 `((value >> i) & 1) == 1` | 못 잡음 |
| 6 | 루프 안 `1UL << (int)flagKey` | 루프 변수 `i` 대신 다른 값을 써서 매번 같은 칸만 확인 | 손으로 루프를 돌려 보면 매번 같은 값이 나옴 | 못 잡음 |

그냥 쓴 숫자의 자료형은 뒤에 붙는 글자(접미사, suffix)가 정한다 (공식 문서).

| 쓴 모양 | 자료형 | 칸 수 |
|---|---|---|
| `1` | int | 32 |
| `1U` | uint | 32 |
| `1L` | long | 64 (부호 있음) |
| `1UL` | ulong | 64 (부호 없음) |

4번의 우선순위는 비트 연산과 관련된 것만 뽑으면 이렇다 (공식 문서: 연산자 우선순위). 위에 있을수록 먼저 계산한다.

| 순서 | 연산자 |
|---|---|
| 1 | `*` `/` `%` |
| 2 | `+` `-` |
| 3 | `<<` `>>` |
| 4 | `<` `>` |
| 5 | `==` `!=` |
| 6 | `&` |
| 7 | `^` |
| 8 | `\|` |

5번은 10진수로 보면 바로 보인다. 302에서 백의 자리만 남기면 3이 아니라 **300**이다. 자리값이 붙은 채로 남는다. AND도 칸 하나만 남겨도 그 칸의 자리값이 붙어 있다.

**디버깅 습관 하나.** 6번은 루프를 손으로 한 줄씩 돌려 보니 바로 보였다. 예시 키 Potion(2) + Epic(2)에서 `(int)flagKey`는 왼쪽 32칸이 잘린 4라서, `flag`가 i와 상관없이 매번 `1UL << 4` = 16이었다. 루프 안에 `Debug.Log($"i={i} flag={flag}")` 한 줄을 넣으면 같은 표를 Console에서 볼 수 있다.

## 8. A와 B는 어떻게 고르나

고르는 기준은 질문 하나다. **"이 칸 묶음에 들어갈 값이 한 번에 하나인가, 여러 개일 수 있나?"**

| 상황 | 들어갈 값 | 고를 것 |
|---|---|---|
| 아이템 하나의 종류와 등급으로 만든 키 | 종류 하나, 등급 하나 | A (숫자 그대로) |
| 화면에 보여 줄 로그 종류 필터 | 전투, 시스템… 여러 개 동시에 | B (비트 하나씩) |
| 8×8 격자의 칸 (앞 노트) | 칸마다 켜짐/꺼짐, 여러 칸 동시에 | B |

키로 쓸 때 A와 B를 나란히 놓으면 이렇다.

| | A | B |
|---|---|---|
| 한 절반에 담을 수 있는 값 | 약 42억 개 (2³²) | 32개 |
| 꺼내기 | 시프트나 마스크 한두 번 | 켜진 칸 찾기 |
| 한 절반에 켜지는 비트 | 상관없음 | 항상 하나. 플래그의 장점(여러 개 켜기)을 안 씀 |

B의 꺼내기가 어색하게 느껴졌던 건 코드 때문이 아니라 **도구를 잘못 골랐다는 신호**였다.

### 조건을 바꿔 보기: Grade가 40개로 늘어나면

| | 결과 | 이유 |
|---|---|---|
| A | 안전 | 숫자로 넣으니 32칸에 약 42억까지 들어감. 왼쪽이든 오른쪽이든 같음 |
| B | Grade 32번부터 깨짐 | 켜야 할 칸이 32 + 32 = 64번 이상이라 64칸 상자 밖으로 떨어져 `gradeFlag`가 0이 됨. 에러 없이 키가 겹침 |

B에서 Grade를 오른쪽에 두었다면 상자 밖으로 떨어지는 대신 **ItemType 칸을 침범**한다. 깨지는 모양이 달라진다.

## 정리

1. ulong 64칸을 왼쪽 32칸(상위 비트)과 오른쪽 32칸(하위 비트)으로 나눠 enum 두 개를 담는다. enum은 이름이 붙은 int라서 비트 모양을 그대로 옮길 수 있다
2. A(숫자 그대로) 만들기: 왼쪽 값은 `(ulong)값 << 32`, 오른쪽 값은 그대로, OR로 합친다. 밀기 전에 ulong으로 바꾼다
3. A 꺼내기는 몫과 나머지다. 왼쪽 값은 `>> 32` 한 번, 오른쪽 값은 왼쪽 지우기(마스크 `(1UL << 32) - 1` / `<< 32` 다음 `>> 32` / 32칸 자료형으로 캐스트)
4. 숫자의 값은 0번 칸부터 읽는다. 오른쪽 값은 지우기만, 왼쪽 값은 옮기기가 필요하고 `>>`가 지우기까지 함께 한다
5. B(비트 하나씩)는 같은 ulong이라도 형식이 다르다. 꺼낼 때 켜진 칸 번호를 찾는 단계가 더 있고, 만드는 메서드와 꺼내는 메서드는 짝이 맞아야 한다
6. 값이 한 번에 하나면 A, 여러 개가 동시에 켜지면 B. 키 만들기에는 A가 맞는 도구다
7. 그냥 쓴 `1`은 int, `-`는 `<<`보다 먼저, AND 결과는 그 칸의 자리값. 이 세 가지는 컴파일러가 잡아 주지 않는다
